# lab-server: TCP и WebSocket

Сервер измерений и управления приборами: один worker на физический порт, общий сервис для TCP и WebSocket,
необязательная запись SQLite. Встроенная фабрика поддерживает Arduino и МЕТАКОН 513/523/533.
Драйвер МЕТАКОН проверен имитацией; проверка на физическом приборе ещё предстоит.

## Быстрый запуск

Из корня репозитория в Windows PowerShell:

```powershell
cargo run --release -- --config examples/arduino.toml
```

[examples/arduino.toml](examples/arduino.toml) задаёт COM3, 57600 бод и TCP **127.0.0.1:7240**.
Перед запуском настройте физический порт под своё устройство. Требуется аргумент `--config`; путь с пробелами заключайте в кавычки.
В открытом TCP-соединении отправьте строки с LF:

```json
{"id":1,"op":"hello"}
{"id":2,"op":"get","key":"furnace1/power"}
```

Ответ hello содержит `"protocol":"lab-server","version":1`. До первого опроса get может вернуть `no_data`.
Остановка — **Ctrl+C**; дождитесь выхода процесса и завершения записи, если она включена.

Без оборудования можно запустить `cargo run --release -- --config examples/websocket.toml`:
этот пример содержит пустой каталог, TCP 7240 и WS 7241.
[examples/lab-server.toml](examples/lab-server.toml) — только архитектурный пример;
драйвер `custom_ascii` не реализован, запуск с ним завершается ошибкой.

## МЕТАКОН 5Х3

[examples/metakon-readonly.toml](examples/metakon-readonly.toml) — шаблон для первого испытания только чтением.
Перед запуском замените `REPLACE_WITH_ACTUAL_COM_PORT` и проверьте адрес, канал, скорость,
масштаб и единицы по прибору. 9600 бод поддерживаются производителем; фактическая настройка неизвестна.
Формат линии — 8N1. SQLite в шаблоне выключен.

```toml
[[devices]]
id = "metakon1"
driver = "metakon"
port = "metakon_bus" # Должен ссылаться на настроенный [[ports]].

[devices.options]
address = 1 # Пример, не установленный адрес прибора.
channel = 0 # Отсчёт от нуля; канал должен существовать на приборе.
process_value_scale = 1.0 # Пока только сырые отсчёты; масштаб ещё нужно подтвердить.
process_value_unit = "" # Не объявлять degC до проверки датчика и десятичной точки.
write_enabled = false
```

Адрес, канал и масштаб обязательны; неизвестные опции, неверные типы и диапазоны отклоняются до открытия портов.
`write_enabled` по умолчанию `false`: все параметры read-only, в том числе при прямом вызове драйвера.
Измерение и выходная мощность опрашиваются раз в секунду; `get` этих ключей читает кеш.
Остальные параметры читаются отдельным запросом.

Доступны `channel_type`, `measurement`, `setpoint`, `proportional_band`, `integral_time`,
`derivative_time`, `output_power`, `pwm_positive`, `pwm_negative`, `upper_setpoint`,
`upper_hysteresis`, `upper_output`, `lower_setpoint`, `lower_hysteresis`, `lower_output`.
Глобальные ключи: `metakon1/measurement`, `metakon1/output_power` и т. д.
При масштабе 1 физические величины имеют тип integer, при другом масштабе — float;
времена в секундах и мощность в процентах остаются integer, состояния выходов — boolean.

CRC, кадры, все регистры, ошибки, отсутствие повторных записей и путь через TCP/PortWorker проверены имитацией.
Реальные настройки линии, масштаб измерения, флаги доступа и поведение записи требуют испытания.
[Порядок испытания 16 ноября](docs/metakon-hardware-test.md) ·
[Регистры, протокол прибора и сравнение доноров](docs/metakon-driver.md).

## Транспорты и идентификаторы

TCP использует UTF-8 NDJSON: один JSON-объект на строку, LF обязателен, CRLF допускается.
Входной кадр ограничен 16 КиБ без LF; частичные чтения собираются до конца строки.

WebSocket включается секцией `[websocket]`: `enabled = true`, `bind = "127.0.0.1:7241"`,
необязательный `allowed_origins = ["http://localhost:3000"]`.
Endpoint — `ws://127.0.0.1:7241/application/v1`, обязательный подпротокол — **lab-server.application.v1**.
Один JSON на Text message без LF; предел сообщения и отдельного frame — 16 КиБ.
Binary не поддерживается. Версия, команды, типы, ошибки и подписки общие с TCP.

Оба listener разрешены только на числовых loopback-адресах. Переданный Origin должен точно совпасть с разрешённым;
отсутствующий Origin допускается. **WebSocket не предоставляет TLS/авторизацию и не должен открываться прямо в интернет.**
Origin не является аутентификацией.

`id` — положительное целое u64, строго возрастающее в пределах соединения.
Отклонённая команда расходует корректный новый ID; неверный JSON, повторные JSON-поля и неверный ID — нет.
Повторный или меньший ID даёт `duplicate_id` без `id`; исходный pending-запрос сохраняется.
Перед исчерпанием u64 нужно новое соединение. Ответы могут приходить в другом порядке; сопоставляйте их по ID.

Ключ всегда глобальный: `device_id/local_parameter`, например `furnace1/power`.
Коротких псевдонимов нет. В локальном имени допустим `/`: `furnace1/designer/seed`.
Драйвер получает локальное имя без префикса прибора.

## Команды

Обязательные для всех команд поля — `id` и `op`; дополнительные поля указаны в таблице.
JSON-примеры запросов нужно отправлять с завершающим LF. Примеры ответов предполагают указанные ID.

| `op` и назначение | Дополнительные обязательные поля | Пример запроса | Успешный ответ |
| --- | --- | --- | --- |
| `hello` — версия протокола | — | `{"id":1,"op":"hello"}` | `{"id":1,"status":"ok","protocol":"lab-server","version":1}` |
| `describe` — каталог параметров и действий | — | `{"id":2,"op":"describe"}` | `id`, `status: "ok"`, массивы `parameters` и `actions` |
| `ping` — проверка связи | — | `{"id":3,"op":"ping"}` | `{"id":3,"status":"ok"}` |
| `get` — получить значение | `key`: строка | `{"id":4,"op":"get","key":"furnace1/heater_temperature"}` | `id`, `status: "ok"`, `key`, `value`, `unit`, `completed_at_unix_ms` |
| `set` — записать значение | `key`: строка, `value`: число или Boolean | `{"id":5,"op":"set","key":"furnace1/power","value":20}` | `{"id":5,"status":"ok"}` |
| `subscribe` — добавить подписки | `keys`: массив строк; либо одиночный `key` | `{"id":6,"op":"subscribe","keys":["furnace1/heater_temperature"]}` | `{"id":6,"status":"ok","keys":["furnace1/heater_temperature"]}` при отсутствии других подписок |
| `unsubscribe` — удалить подписки | `keys`: массив строк | `{"id":7,"op":"unsubscribe","keys":["furnace1/heater_temperature"]}` | `{"id":7,"status":"ok","keys":[]}` при удалении последней подписки |
| `invoke_action` — выполнить действие без аргументов | `key`: глобальное имя действия | `{"id":17,"op":"invoke_action","key":"furnace1/apply"}` | `{"id":17,"status":"ok"}` |


## Типы и ответы

`describe.parameters` содержит `key`, `type`, `min`, `max`, `unit`, `writable`, `poll_period_ns`.
`describe.actions` содержит `key`, `description`; при отсутствии действий это пустой массив.
`poll_period_ns` — наносекунды либо null, если периодического опроса нет.

| Тип | JSON и правила |
| --- | --- |
| integer | Целочисленный литерал в диапазоне i64; точность сохраняется |
| float | Дробный или экспоненциальный литерал, конечное значение |
| boolean | Только true/false; min и max равны null, unit — пустая строка |

Для чисел min/max включительны. Неявных преобразований нет: `20` и `20.0` различаются;
числа и строки не заменяют Boolean. Запись требует writable и соответствия типу/диапазону.
Arduino предоставляет четыре опрашиваемых Operator-параметра, 19 Designer-параметров по запросу и действия apply/reset;
булевых параметров в его каталоге нет. Полный каталог и особенности float32 — в [протоколе](docs/protocol.md).

`get` опрашиваемого параметра возвращает кеш, включая последнюю ошибку чтения; при отсутствии измерения — no_data.
Для параметра без опроса выполняется отдельное чтение. Альтернативные ответы:

```json
{"id":4,"status":"ok","key":"furnace1/heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"id":4,"status":"no_data","key":"furnace1/heater_temperature"}
{"id":4,"status":"error","key":"furnace1/heater_temperature","error":"Empty response","completed_at_unix_ms":1700000000000}
```

Успешные set/invoke_action возвращают ACK с id и status. При остановленном порте кеш не выдаётся.

## Подписки и события

subscribe добавляет ключи, unsubscribe удаляет их; доступны только периодически опрашиваемые параметры.
Совместимый одиночный `key` поддержан только для subscribe; вместе с `keys` его передавать нельзя.
Пустой `keys: []` ничего не меняет. Повторы удаляются, ACK содержит полный отсортированный набор подписок.
Весь запрос проверяется атомарно; повторная подписка сохраняет границу уже активного ключа.

ACK subscribe предшествует новым событиям; публикации до активации не воспроизводятся.
После ACK unsubscribe события удалённого ключа не поступают; уже поставленные на отправку события могут предшествовать ACK.
Граница относится к публикации fanout, а не ко времени физического измерения.
События без id сохраняют порядок публикации:

```json
{"event":"measurement","status":"ok","key":"furnace1/heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"event":"measurement","status":"error","key":"furnace1/heater_temperature","error":"Empty response","completed_at_unix_ms":1700000001000}
```

Время — завершение измерения, не отправка клиенту. При ошибке вместо value/unit передаётся error.
Потеря на порту A не затрагивает клиента, подписанного только на B; смешанная подписка A+B завершается целиком.
При u64::MAX непрерывность потеряна и для новой подписки.

## Ошибки и ограничения

Ошибка запроса обычно имеет поля `id`, `status: "error"`, `error`; для ошибки конкретного ключа может присутствовать `key`.
Если ID нельзя однозначно извлечь, он отсутствует. `duplicate_id`, ошибки кадра и завершения потока приходят без `id`.
Например: `{"status":"error","error":"duplicate_id"}` или `{"status":"error","error":"observation_data_lost"}`.

| Группа | Значения `error` и смысл |
| --- | --- |
| Кадр | `empty_frame`, `frame_too_long`, `invalid_utf8`, `incomplete_frame` (EOF до LF); соединение завершается |
| JSON | `invalid_json`, `expected_object`, `duplicate_key` |
| Поля запроса | `invalid_id`, `unsupported_op`, `invalid_key`, `invalid_value`, `invalid_keys` — неверное или отсутствующее поле |
| Уникальность ID | `duplicate_id` — повторный или меньший ID |
| Параметр и запись | `unknown_key`; `Parameter is read-only`; `Value does not match parameter spec` |
| Подписки | `not_subscribable` — нет периодического опроса; `too_many_subscriptions` — превышен лимит |
| Очереди | `too_many_pending` — лимит ожидающих запросов клиента; `runtime_busy` — очередь команд заполнена; `runtime_unavailable` — порт недоступен или остановлен |
| Ожидание | `runtime_timeout`, `outcome_unknown` — различия для `set` и `invoke_action` описаны ниже |
| Поток наблюдений | `observation_data_lost` — потеря данных; `observation_stream_closed` — закрытие без обнаруженного переполнения |

Ошибки чтения содержат текст драйвера или ввода-вывода, например `Empty response`; это не закрытый перечень кодов.
Ожидание `set`, `invoke_action` и отдельного чтения `get` ограничено 10 с, включая очередь.
Для `set` и `invoke_action` используется общий механизм `SetExecution`:

- `runtime_timeout`: исполнение не началось; просроченная команда не будет отправлена устройству.
- `outcome_unknown`: исполнение началось, но результат неизвестен из-за таймаута, потери ответа или ошибки драйвера. **Автоматически повторять операцию нельзя.**
- Уже доступный результат имеет приоритет над таймаутом; поздний результат не порождает второго ответа.

При переполнении очереди порта подписанный на него клиент, а при персональном переполнении владелец очереди получает `observation_data_lost`, и повреждённый поток завершается.
После этого нужно новое соединение и новая подписка. Потеря при активной подписке не сбрасывается через `unsubscribe` → `subscribe` до уведомления.
Потеря в период без подписок не мешает последующей подписке (кроме насыщения u64::MAX); клиенты без подписок сохраняют соединение и pending-команды.
Переполнение выходного буфера или транспортная ошибка могут привести к закрытию без сообщения об ошибке.
EOF не доказывает полноту доставки измерений или неисполнение ожидающего `set` / `invoke_action`.

| Ресурс | Лимит |
| --- | --- |
| Одновременные TCP + WS клиенты | 32 суммарно, включая WS handshake; лишние соединения закрываются |
| Pending-запросы на клиента | 64 |
| Подписки на клиента | 64 ключа |
| Выходной буфер клиента | 64 KiB |
| Очереди команд и наблюдений PortWorker | По 128 элементов на порт |
| Персональная очередь наблюдений | 128 элементов |

## Конфигурация, запись и устройство сервера

[Архитектура и конфигурация](docs/architecture.md) описывает валидацию TOML, порты, планировщик,
границы потерь, порядок shutdown, включение Recorder и схему SQLite.
[Подробный протокол](docs/protocol.md) содержит WebSocket-лимиты, Arduino Designer и примеры общего Session API.
[Отчёт очистки](docs/legacy-cleanup-review.md) перечисляет изменения Rust API и соответствие тестов.

Неизвестные поля схемы и драйверы отклоняются. Непустые options у Arduino запрещены.
Периоды в poll_periods_ms задаются локальными именами и положительными миллисекундами; отключения опроса через TOML нет.
Недоступный COM-порт допускает запуск остальных портов и API с сохранением каталога. Автоматического переподключения нет.
SQLite выключена по умолчанию; относительный путь БД считается от рабочего каталога процесса.

[Примеры Steel](clients/steel/examples/thermal-plant/get.scm) рассчитаны на examples/arduino.toml:
furnace1 и порт 7240. set.scm изменяет мощность; запускайте такие примеры только осознанно.
Эти сценарии не предназначены для сервера коротких имён.
