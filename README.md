# lab-server: TCP-протокол

lab-server предоставляет TCP-доступ к измерениям и управлению параметрами Arduino.
Клиент может запрашивать значения, изменять доступные для записи параметры и получать поток измерений.
Протокол поддерживает `integer`, `float` и `boolean`; существующий Arduino-драйвер пока не предоставляет булевых параметров.

## Запуск

В Windows PowerShell, из корня проекта:

```powershell
cd D:\rust_projects\lab-server
$env:CARGO_TARGET_DIR = 'D:\rust_projects\lab-server-agent-build'
cargo run --release
cargo run --release -- --config examples/arduino.toml
```

Это два альтернативных режима. Без аргументов сохраняется прежний runtime Arduino:
`COM3`, **57600** бод, таймаут 3 с, пауза после открытия 2 с, TCP `127.0.0.1:7240`,
локальные ключи `sample_temperature`, `power` и т. д.

С `--config` используется многопортовый запуск. Рабочий пример [examples/arduino.toml](examples/arduino.toml)
задаёт тот же Arduino и TCP-адрес, но ключи глобальные: `furnace1/sample_temperature`, `furnace1/power`.
Например, запрос: `{"id":1,"op":"get","key":"furnace1/power"}`. Версия TCP-протокола остаётся 1.
Путь с пробелами заключайте в кавычки. Остановка процесса — `Ctrl+C`.

### Запуск из TOML (этап 4B)

`lab_server::startup` создаёт драйверы, применяет периоды, открывает порты и связывает существующие
`PortWorker`, `DeviceRegistry`, `CommandRouter`, `ObservationAggregator` и один общий `MultiDeviceTcp`.
Все поля последовательного порта применяются через `serialport`. Каждый порт открывается один раз;
все ссылающиеся на него приборы работают через один worker. Совместимость протоколов обеспечивает пользователь.
Пауза Arduino 2 с выполняется после открытия, один раз на общий порт; опрос начинается после подготовки всех портов.

Поддержан только `driver = "arduino"`. Он пока не принимает `options`: любая непустая таблица — ошибка.
[examples/lab-server.toml](examples/lab-server.toml) остаётся архитектурным примером: **его нельзя использовать
для успешного запуска**, поскольку `metakon` и `custom_ascii` ещё не реализованы.

Ошибки TOML, неизвестные драйверы, неверные настройки и неизвестные параметры `poll_periods_ms`
прерывают запуск до открытия оборудования. Ошибка привязки TCP listener также прекращает запуск.
Недоступный или занятый COM-порт допускает частичный запуск: причина сохраняется в реестре и печатается в stderr,
все его приборы остаются в `describe`, а `get` и корректные запросы `set` возвращают `runtime_unavailable`.
TCP работает даже при отказе всех портов. Остановка worker не останавливает соседние порты или listener.
Автоматических повторов открытия и переподключения нет.

`startup::start_with` принимает фабрику драйверов и функцию открытия для тестирования без оборудования.
`StartedServer::run` обслуживает TCP и агрегатор; `run_until` позволяет завершить цикл флагом,
закрыть клиентские сокеты и дождаться workers после текущих ограниченных по времени операций I/O.
При отсутствии наблюдений цикл ожидает 5 мс, в том числе после завершения всех workers.
В режиме `--config` обработчик `Ctrl+C` только устанавливает `AtomicBool`. Сервер прекращает принимать
соединения, закрывает и ожидает клиентские потоки (новых команд больше нет), запрашивает остановку
всех PortWorker и продолжает читать агрегатор, пока драйверы завершают текущие операции.
Приёмники остаются живыми, очереди освобождаются до EOF, включая последние измерения, `DataLost`
и `PortStopped`; при временно пустом агрегаторе цикл ожидает 5 мс. Затем сервер выполняет `join()`
workers и вызывает `Recorder::shutdown()`. Результат закрытия проверяется;
listener освобождается при возврате. Ошибки основного цикла также проходят этот путь завершения.
Одновременные ошибки интеграции и закрытия сохраняются в результате; ненулевой exit code означает ошибку.
Принудительное прерывание зависшего синхронного драйвера не выполняется; сохраняются его конечные I/O-таймауты.
Библиотечный `run()` сам не устанавливает обработчик сигнала; для управляемого завершения нужен `run_until()`.
Прежний запуск без аргументов сохраняет прежнее поведение.

## Общее ядро сессии (этап 5A)

`session::Session` принимает один завершённый JSON-текст через `receive_message`,
выдаёт отдельные JSON-сообщения без LF через `next_message` и обслуживает существующие
pending-запросы через `collect_ready`. `bind_observations` связывает сессию с одним
`ObservationReceiver` **до первой подписки**; `collect_observations` читает тот же приёмник
порциями до 32 публикаций. Приёмник нужно сохранять до завершения сессии.

`service::DeviceService` содержит общий `CommandRouter`, каталог, кеш и `ObservationFanout`.
Его `receive_message` передаёт JSON в сессию с этим контекстом. Все транспорты должны
использовать один экземпляр сервиса: второй кеш, агрегатор или обработчик команд не нужен.
`tcp::MultiDeviceTcp` остаётся совместимым именем этого же типа, включая прежние методы TCP.

Пример границы для владельца транспорта (без открытия сокетов или оборудования):

```rust,ignore
use lab_server::session::Session;
use std::time::Instant;

// service: &lab_server::service::DeviceService
let mut session = Session::new(64, 64 * 1024);
let observations = service.register_client()?;
session.bind_observations(&observations);

// Повторяется владельцем транспорта, даже когда новых запросов нет.
session.collect_ready(Instant::now())?;
service.receive_message(&mut session, r#"{"id":1,"op":"hello"}"#, Instant::now())?;
session.collect_observations(&observations)?;
if let Some(json_text) = session.next_message()? {
    // Передать один JSON-текст, ограничивая собственный буфер транспорта.
}
// После чистого EOF: session.close_input(); затем обслуживать pending и выход
// до session.is_finished(). При аварии транспорта владелец освобождает сессию.
```

`protocol::Request`, `parse_request` и `observation_json` общие для всех транспортов;
прежние `TcpRequest`, `parse_tcp_request` и корневой `observation_json` сохранены.
`connection::TcpConnection` сохраняет публичные методы и поле `session`.
`connection::ClientSession` — тот же `SessionState`, с дополнительным состоянием
TCP-адаптера вместо `()`; прежние поля и `receive(bytes)` / `dispatch_incoming` доступны.
Только адаптер содержит NDJSON-декодер, разбирает ошибки фрейминга, дописывает LF и
выполняет частичные записи сокета. Само ядро не использует `TcpStream` или `FrameDecoder`.

Исходящая FIFO хранит законченные тексты, а не слитый поток байтов. Её бюджет по-прежнему
равен **64 КиБ ожидающих отправки байтов: UTF-8 сообщения + 1 байт LF**. Для транспорта
сообщений этот дополнительный байт также резервируется; `next_message` освобождает всю
стоимость сообщения. TCP освобождает только фактически записанные байты, сохраняя позицию
при `WouldBlock`, включая позицию перед LF. Получить целое сообщение после частичной TCP-записи
нельзя: возвращается ошибка, предотвращающая повторную отправку префикса.
Во время частичной записи сохраняется исходный текст переднего сообщения; поэтому хранение
текстов ограничено бюджетом очереди плюс не более одного частично отправленного сообщения
(помимо ограниченных накладных расходов объектов FIFO). Это бюджет ожидающих байтов, а не лимит RAM.

Порядок обслуживания TCP сохранён: готовые завершения pending, ответы на разобранные запросы,
затем наблюдения. ACK подписки предшествует её новым измерениям; номера активации, накопленная
потеря после unsubscribe/subscribe и изоляция портов остались в существующих session/fanout.
Чистый EOF прекращает новые запросы и поток измерений, но позволяет получить окончательные
ответы pending. Терминальная ошибка потока не создаёт фиктивных ответов `set`.
`PendingRequests`, `Pending`, `SetExecution`, таймауты и правила `outcome_unknown` не изменены.

WebSocket, новый listener, TOML, TLS, X-Token и Tuna на этапе 5A не добавлены.
На этапе 5B адаптеру потребуются собственные ограничения входного сообщения и внутреннего
буфера отправки, обработка WS close/error и справедливое обслуживание pending/наблюдений
при отсутствии входящих запросов. Вход TCP по-прежнему ограничен 16 КиБ; ядро получает уже
выделенный текст и не выполняет транспортный фрейминг. При переполнении выхода ядро становится
терминальным; транспорт завершает отправку уже принятого префикса, если соединение это позволяет.

## Включение SQLite в TOML

Добавьте отдельную секцию верхнего уровня к конфигурации (например, в конце файла):

```toml
[recording]
enabled = true
path = "../lab-server-agent-build/measurements.sqlite"
queue_capacity = 1024
```

Без `[recording]` или при `enabled = false` база не открывается. В присутствующей секции `enabled`
обязателен. При `enabled = true` требуется непустой `path`; `queue_capacity` необязателен и по умолчанию
берётся из `RecorderOptions` (1024). Нулевая ёмкость и неизвестные поля отклоняются, даже если запись выключена.
Размер пакета, интервал и busy timeout пока стандартные. `from_toml()` и `validate()` не создают базу.
Исходный [examples/arduino.toml](examples/arduino.toml) работает без включения записи.

**Относительный путь базы разрешается относительно текущего рабочего каталога процесса, а не TOML-файла.**
При запуске из `D:\rust_projects\lab-server` приведённый путь ведёт в
`D:\rust_projects\lab-server-agent-build\measurements.sqlite`. Родительский каталог должен существовать.
Можно указать абсолютный путь (в TOML удобно использовать `/` либо одинарные кавычки).

Startup сначала проверяет конфигурацию и драйверы, привязывает TCP listener и открывает SQLite,
затем открывает физические порты и запускает workers. Если включённую SQLite открыть нельзя,
запуск завершается ошибкой, listener освобождается, оборудование ещё не открывалось.
Недоступность отдельных или всех COM-портов не препятствует запуску TCP и Recorder.

Один агрегатор извлекает каждое событие один раз. Startup передаёт его Recorder и затем TCP в исходном
порядке, без ожидания SQLite и независимо от TCP-подписок. Сохраняются все варианты событий,
ошибки чтения, исходный локальный `Observation.source` и отдельный глобальный ключ.
Recorder использует один writer на весь сервер; число приборов не добавляет потоков записи.
Измерения в `measurements` поступают из периодического опроса PortWorker через агрегатор;
ответы на отдельные команды `get`/`set` сами по себе не являются новым потоком записи.

При переполнении (`Full`) TCP и опрос продолжаются; при первом отказе в stderr однократно выводится
предупреждение. Потерю считает только Recorder; финальный снимок попадает в SQLite при успешном завершении.
После успешного `Recorder::shutdown()` в stderr выводится `Recording summary`: `session_id`,
`accepted_records`, `dropped_events`, `dropped_data_lost_events`, `rejected_invalid_data` и `incomplete`.
Статистика берётся из `RecordingSummary`; успешное закрытие возможно и при `incomplete=true`.
При ошибке диска Recorder переходит в `Failed`,
startup сохраняет причину и однократно печатает диагностику, продолжая TCP и работу приборов.
Автоматического возобновления записи нет. При `InvalidData` отдельно учитывается отказ,
однократно выводится первая причина; следующие корректные измерения записываются.
Обе ситуации (`Failed` и `InvalidData`) приводят к ошибке результата startup после завершения.
Уже сохранённые сведения сохраняются, но при отказе SQLite наличие финальных счётчиков на диске не гарантируется.

Для завершения используйте `Ctrl+C` и дождитесь выхода процесса. Успешная постановка в очередь ещё
не означает запись на диск. Успешный `Recorder::shutdown()` подтверждает дописывание всех принятых
записей и финальных сведений о потерях, **но не отсутствие потерь**. При `Full` завершение может быть
успешным с неполным сеансом; проверяйте счётчики и события. `recorder_incomplete` описывает потери
Recorder, а потери PortWorker отражены отдельно в `DataLost`. `DataLost` не определяет точную позицию разрыва.
Принудительное уничтожение процесса, закрытие окна консоли и отключение питания не гарантируют
сохранение очереди в памяти. TCP API запросов к истории отсутствует.

Проверить фактическую базу можно любым SQLite-клиентом, например `sqlite3` (CLI устанавливается отдельно):

```powershell
sqlite3 ../lab-server-agent-build/measurements.sqlite
```

```sql
SELECT id, started_at_ns, ended_at_ns, recorder_incomplete,
       recorder_dropped_events, recorder_dropped_data_lost_events
FROM sessions ORDER BY id;
SELECT session_id, port_id, global_key, local_source, value_type,
       integer_value, real_value, boolean_value, read_error, completed_at_ns
FROM measurements ORDER BY id DESC LIMIT 20;
SELECT session_id, origin, event_type, details_json
FROM events ORDER BY id DESC LIMIT 20;
-- Последний накопленный снимок Recorder для каждого сеанса (не сумма снимков):
SELECT session_id, json_extract(details_json, '$.dropped_events') AS overflow,
       json_extract(details_json, '$.rejected_invalid_data') AS invalid_data
FROM events WHERE id IN (
    SELECT max(id) FROM events WHERE event_type = 'RecorderDataLost' GROUP BY session_id
);
```

## SQLite Recorder Core (этап 4A)

`lab_server::recorder` — самостоятельный библиотечный компонент. Его создание не открывает COM-порты
и не зависит от TCP-подписчиков. В режиме `--config` startup подключает его при включённой секции
`[recording]`; запуск без `--config` запись не поддерживает.

Используется `rusqlite 0.40.2` с `bundled`: SQLite собирается вместе с проектом, отдельная установка SQLite
под Windows не нужна. Для сборки требуется обычный для Rust MSVC инструмент C/C++.

### API

- `Recorder::open(path, queue_capacity)` создаёт writer и ждёт открытия базы/проверки схемы/создания сеанса.
  Ошибка возвращается вызывающему коду. Родительский каталог должен существовать.
- `Recorder::with_options(path, RecorderOptions)` дополнительно задаёт размер пакета, интервал сброса и SQLite busy timeout.
  По умолчанию: очередь 1024, пакет 128, интервал 100 мс, busy timeout 250 мс. Нулевые очередь, пакет и интервал запрещены.
- `recorder.handle()` возвращает клонируемый потокобезопасный `RecorderHandle`.
- `handle.try_record(AggregatorEvent)` принимает уже полученное событие агрегатора;
  `try_observation(port_id, global_key, Observation)` — удобный вариант для измерения.
  Startup клонирует одно событие для TCP и Recorder; повторный опрос не требуется.
- `handle.state()` возвращает `Running`, `Closing`, `Stopped` или `Failed(RecorderError)`;
  `handle.losses()` — накопленные `LossInfo`, `handle.session_id()` — идентификатор сеанса.
- `recorder.shutdown()` закрывает приём, дописывает очередь и пакет, сохраняет потери и завершение сеанса,
  закрывает соединение SQLite и ожидает writer. Результат — `RecordingSummary` либо типизированная ошибка.
  Сохранённые handles остаются пригодны для чтения окончательного состояния.

Пример использования библиотечного API, без оборудования:

```rust,no_run
use lab_server::model::{Observation, Value};
use lab_server::recorder::Recorder;
use std::time::SystemTime;

fn record_one(path: &std::path::Path) -> Result<(), Box<dyn std::error::Error>> {
    let recorder = Recorder::open(path, 1024)?;
    let handle = recorder.handle();
    handle.try_observation("arduino", "furnace1/power", Observation {
        source: "power".into(),
        unit: "%".into(),
        completed_at: SystemTime::now(),
        reading: Ok(Value::Integer(30)),
    })?;
    let summary = recorder.shutdown()?;
    assert_eq!(summary.accepted_records, 1);
    Ok(())
}
```

### Очередь, транзакции и гарантии

Один поток владеет одним соединением SQLite. В памяти ограничены очередь и текущий пакет;
ограничение задано числом событий, а не байтами строк в их полезной нагрузке.
`try_record` использует `sync_channel::try_send` и короткий mutex для согласования приёма,
потерь и остановки. Mutex никогда не удерживается во время SQLite I/O или ожидания места.
API не является lock-free и не обещает жёсткого real-time дедлайна.

Пакет записывается одной транзакцией при достижении размера либо интервала накопления.
При малом потоке частичный пакет регулярно фиксируется; пустой writer ожидает `recv_timeout`.
Интервал ограничивает накопление, но не задержки файловой системы. Используются WAL, `synchronous=FULL`,
внешние ключи и подготовленные запросы. База должна находиться на локальной файловой системе с поддержкой WAL.

`Ok(())` от приёма означает только постановку в очередь. Успешный `shutdown` означает, что все принятые записи
и окончательный снимок потерь зафиксированы, SQLite закрыта. При ошибке такого обещания нет.
При штатной работе и завершении повторной записи принятых элементов нет; повторная самостоятельная отправка
вызывающим кодом считается новым событием — дедупликация по содержимому не выполняется.
`Drop` также закрывает и ожидает writer, но не возвращает ошибку: для подтверждения сохранения нужен `shutdown`.
Открытие и завершение могут ждать SQLite; только передача событий исключает это ожидание.

Переполнение немедленно возвращает `SubmitError::Full`. Вне очереди хранятся два насыщаемых счётчика:
`dropped_events` и его подмножество `dropped_data_lost_events` — число недоставленных уведомлений агрегатора
о потерях PortWorker. Отдельный насыщаемый `rejected_invalid_data` считает события, отклонённые из-за
`InvalidData` (непредставимое время, NaN/бесконечности). При таком отказе возвращается прежний `InvalidData`,
корректные события продолжают приниматься. Все три счётчика монотонны и не сбрасываются чтением,
освобождением очереди или успешной записью. `is_incomplete()` проверяет `dropped_events > 0` либо
`rejected_invalid_data > 0`. Отказы `Closed`/`Failed` эти счётчики не увеличивают.
`LossInfo::is_incomplete()` остаётся истинным, включая насыщение `u64::MAX` (значение означает «не менее»).
Writer переносит новые снимки в событие `RecorderDataLost` и поля сеанса, даже если само уведомление потери
не помещалось в очередь. Для этого не требуется ещё одно успешное поступление от отправителя.

`DataLost` с `origin=port_worker` хранит исходный `loss_epoch`. `RecorderDataLost` с `origin=recorder`
хранит отдельные накопленные счётчики и `port_worker_continuity_unknown`, если был потерян сам `DataLost`.
JSON содержит `rejected_invalid_data` в виде десятичной строки. Схема остаётся версии 1: столбцы
`recorder_dropped_events` и `recorder_dropped_data_lost_events` по-прежнему относятся только к переполнению,
а `recorder_incomplete` учитывает также `InvalidData`. В старых событиях этапа 4A этого JSON-поля нет;
их нулевые счётчики не доказывают отсутствие отказов `InvalidData`, которые раньше не учитывались.
При переполнении не гарантируется сохранение конкретного порта и полезной нагрузки отброшенного события:
неполнота консервативно относится ко всему сеансу Recorder. Точная позиция пропуска неизвестна,
счётчики снимков нельзя суммировать, искусственные временные отметки пропущенных измерений не создаются.
Если SQLite отказывает до записи снимка, сведения о потерях остаются в handles, но их наличие на диске не гарантируется.

Критическая ошибка SQLite, включая истечение busy timeout, переводит Recorder в `Failed`.
Сохраняются операция, extended SQLite code и сообщение. Новые отправки получают `SubmitError::Failed`,
`shutdown` возвращает ошибку; автоматических повторов или восстановления нет.
Незавершённая транзакция откатывается, ранее зафиксированные пакеты остаются.
Паника writer при стандартном unwind также преобразуется в ошибку; аварийное завершение процесса,
`panic=abort`, сбой диска или питания не дают гарантий для очереди в памяти.

### Схема версии 1

Файл имеет `PRAGMA application_id = 0x4c414252` (`LABR`) и `PRAGMA user_version = 1`.
Чужие базы и неизвестные версии отклоняются, миграций пока нет. Повторное открытие добавляет сеанс,
не удаляя старые строки. Таблицы `STRICT` и `CHECK` не позволяют смешивать колонки разных типов значения.

| Таблица | Содержимое |
| --- | --- |
| `sessions` | `id`, `started_at_ns`, `ended_at_ns`; `recorder_incomplete` и два накопленных счётчика потерь Recorder |
| `measurements` | `session_id`, `port_id`, `global_key`, исходный `local_source`, `completed_at_ns`, `unit`, `value_type`, отдельные `integer_value`, `real_value`, `boolean_value`, `read_error` |
| `events` | `session_id`, `registered_at_ns`, `event_type`, `origin`, необязательный `port_id`, структурированный `details_json` |

У каждой строки измерения и события есть собственный `id`. Индексы: `(session_id, global_key, completed_at_ns)`
для измерений и `(session_id, id)` для событий. `ended_at_ns IS NULL` означает отсутствие зафиксированного
завершения; отметка окончания записывается после полного дренирования. Ошибка финализации возвращается вызывающему коду.

Все колонки времени — знаковые Unix-наносекунды `i64` (примерно 1677–2262 годы).
Сохраняется исходный `Observation.completed_at`, включая время до Unix epoch, без округления в Recorder;
точность исходного `SystemTime` зависит от платформы (Windows — 100 нс).
Выход за диапазон возвращает `SubmitError::InvalidData(TimestampOutOfRange)` до приёма.
Для диагностических событий время регистрации берётся при приёме, для снимка потерь — при его записи;
оно не обозначает время пропущенных измерений. Системные часы могут переводиться назад.

Integer сохраняется как SQLite INTEGER без преобразования в Float, включая оба предела `i64`.
Float хранится как REAL, Boolean — отдельный INTEGER 0/1 с меткой типа `boolean`.
NaN и бесконечности измерений явно отклоняются (`NonFiniteFloat`). Ошибка чтения сохраняется как
`value_type=error` с исходными временем, единицей и текстом ошибки; ожидаемый тип отсутствует в самом `Observation`.
Счётчики `u64` и `loss_epoch` записываются десятичным TEXT, чтобы сохранить весь диапазон.

События: `DataLost`, `PortStopped`, `InvalidObservation`, `SourceClosedWithoutStop`, `RecorderDataLost`.
Для остановки сохраняются причина и сведения `DriverError`; для неверного сопоставления — прибор,
исходное наблюдение и `MappingError`. В диагностическом JSON InvalidObservation целые записаны десятичными строками,
Float — IEEE-754 bits в hex, время — знак относительно epoch, секунды и наносекунды: даже неверный payload
с NaN или временем вне диапазона измерительной колонки не теряет диагностическую информацию.

Тесты не открывают оборудование. Повтор конкурентных сценариев вместе с остальными тестами Recorder:

```powershell
$env:CARGO_TARGET_DIR = 'D:\rust_projects\lab-server-agent-build'
1..20 | ForEach-Object { cargo test --lib recorder::tests; if ($LASTEXITCODE -ne 0) { throw 'recorder debug failed' } }
1..20 | ForEach-Object { cargo test --release --lib recorder::tests; if ($LASTEXITCODE -ne 0) { throw 'recorder release failed' } }
```

## Статическая конфигурация (этап 3A)

Модуль `lab_server::config` читает, разбирает и проверяет TOML.
Запуск с `--config` дополнительно проверяет драйверы и создаёт runtime, как описано выше.

Модель разделяет физическое соединение и логический прибор:

- `ServerConfig`: `tcp`, список `ports`, список `devices` и необязательная секция `recording`.
- `TcpConfig`: `bind` в виде числового IP-адреса с портом, например `127.0.0.1:7240` или `[::1]:7240`.
- `PortConfig`: `id`, физическое имя `name`, `baud`, `data_bits`, `parity`, `stop_bits`, `flow_control`, `timeout_ms`.
- `DeviceConfig`: `id`, имя `driver`, ссылка `port` на `ports.id`, необязательные `options` и `poll_periods_ms`.

Несколько приборов могут ссылаться на один порт, в том числе с разными драйверами.
Протокол выбирается драйвером прибора; поля `protocol` у порта нет.
Парсер хранит имена драйверов без проверки реализации; при запуске неизвестные имена отклоняются фабрикой.
Совместимость протоколов на общей линии остаётся ответственностью пользователя.

`devices.options` — произвольная TOML-таблица: вложенные таблицы, массивы, строки, целые, дробные числа, Boolean и даты/время
сохраняют свои типы. Поле `address` необязательно; его значение и уникальность здесь не проверяются.
Неизвестные поля основной схемы отклоняются, чтобы выявлять опечатки; это правило не распространяется на содержимое `options`.
Все поля основной схемы обязательны, кроме `options` и `poll_periods_ms` (по умолчанию пусты),
а также необязательных полей записи, описанных выше.
Списки `ports` и `devices` можно явно задать пустыми.

Для переопределений периодов опроса предусмотрена таблица внутри конкретного прибора:

```toml
[devices.poll_periods_ms]
sample_temperature = 1000
power = 2000
```

Ключи — непустые локальные имена сигналов, значения — положительные целые миллисекунды.
При запуске имена проверяются по каталогу драйвера, периоды применяются через `DeviceInstance::set_poll_period`.
Переопределение влияет только на указанный экземпляр прибора.
Отсутствие записи означает сохранение периода по умолчанию драйвера; отключение опроса этим форматом не задаётся.

Проверяются уникальность `port.id` и `device.id`, непустые имена и ссылки, существование указанного `port.id`,
отсутствие `/` в `device.id`, а также отсутствие повторяющегося `ports.name`.
Имена и идентификаторы сравниваются точно, с учётом регистра; разные имена одного физического устройства не распознаются.
Для последовательного соединения допустимы `baud > 0` (в пределах `u32`), `data_bits` 5–8,
`parity` = `none`/`odd`/`even`, `stop_bits` = 1/2, `flow_control` = `none`/`software`/`hardware`, `timeout_ms > 0`.
Поддержка конкретной скорости или сочетания настроек оборудованием здесь не проверяется.
TCP разрешён только на loopback (`127.0.0.0/8`, `::1`); DNS-имена не поддерживаются. TCP-порт допускает 0–65535, включая 0 для выбора порта ОС.

API: `ServerConfig::from_toml(&str)` и `ServerConfig::load(path)` возвращают `Result<ServerConfig, ConfigError>` после проверки.
`config.validate()` повторно проверяет модель после изменений в памяти.
`ConfigError` различает ошибки чтения файла, разбора TOML и валидации. Возвращается первая ошибка:
для TOML указывается место в тексте, для валидации — поле вида `devices[1].port`.
Эти операции не открывают COM-порты, не привязывают TCP-сокет, не создают worker и не проверяют наличие приборов.

## PortWorker (этап 3B)

`lab_server::port_worker` используется многопортовым запуском из TOML.
Без аргументов `main` открывает `COM3`, 57600 бод и запускает прежний runtime Arduino.
Общие `model`, `driver` и `pending` теперь объявлены в library; binary использует те же типы и `SetExecution`.

`PortWorker<P: DeviceIo>` принимает один уже настроенный объект I/O в исключительное владение.
Каждый `DeviceInstance` хранит собственный `Box<dyn Driver + Send>`, идентификатор и каталог `ParameterDescription`.
Драйверы могут совпадать или различаться. Параметры порта общие; worker сейчас не меняет их между транзакциями.
Драйвер получает изменяемую ссылку на общий `DeviceIo` только на время своего вызова.
Следующая операция начинается после полного возврата предыдущего вызова.
`DeviceObservation` содержит отдельный `device_id`; `Observation.source` остаётся локальным именем параметра.
Таким образом, одинаковое имя `value` у двух приборов не требует изменения действующих глобальных ключей.

Основной API:

- `DeviceInstance::new(id, driver)` проверяет каталог; `set_poll_period(parameter, Option<Duration>)` задаёт период конкретного сигнала или отключает его опрос.
- `PortWorker::new(io, devices, command_capacity, observation_capacity)` возвращает worker и `PortChannels` с командным handle и приёмником наблюдений. Ёмкости должны быть положительными.
- `worker.run()` выполняется в вызывающем потоке и возвращает `StopReason`. Для отдельного потока worker можно передать в `thread::spawn`, если I/O реализует `Send`.
- Клонируемый `PortHandle` принимает `read(id, device, parameter, deadline)` и `set(id, device, parameter, value, deadline)` без ожидания места в очереди. Переполнение возвращает `SubmitError::Full`; остановленный порт — `SubmitError::Stopped`.
- Принятый запрос возвращает существующий `Pending`; вызывающая сторона обрабатывает его через `Pending::poll`. Дедлайн включает ожидание в очереди. Удаление `Pending` само по себе не отменяет запись.
- `shutdown()` закрывает приём команд и пробуждает worker даже при заполненной очереди или отсутствии задач. После текущего вызова драйвера ожидающие команды получают `PortStopped`. Закрытие всех отправителей также завершает worker.

Планировщик хранит одну запись на каждый опрашиваемый параметр. Когда одновременно готовы команда и просроченный опрос,
они чередуются по одной операции. Выбирается ближайший срок; внутри группы равных сроков приборы обходятся по кругу,
а начальный прибор меняется между группами. Пропущенные периоды перескакиваются за O(1), с сохранением фазы,
без очереди пропущенных опросов. При отсутствии готовой работы используются `recv`/`recv_timeout`.
Справедливость относится к числу операций; длительный вызов драйвера задерживает весь свой порт.

`DriverError` содержит текст и состояние физического потока:

| Состояние | Последствие для нового worker |
| --- | --- |
| `Synchronized` | Транзакция гарантированно завершена либо I/O не начинался; ошибка чтения попадает в соответствующее наблюдение, другие приборы продолжают работать |
| `Desynchronized` | Граница транзакции неизвестна; дальнейший физический обмен прекращается, очередь получает явные отказы |
| `Disconnected` | Соединение потеряно; worker прекращает обмен и отказывает ожидающим командам |

Неопределённые и строковые ошибки трактуются как `Desynchronized`; таймаут I/O также не считается безопасным завершением.
Arduino сообщает `Synchronized` для ошибок полностью принятого ответа с ожидаемым ID; неполная строка без LF и неверный ID не подтверждают синхронизацию.
При `Desynchronized`/`Disconnected` возврата к обмену в этом worker нет. Запоздалые ответы не очищаются и не передаются следующему драйверу:
порт прекращает работу. Автоматическое восстановление, переподключение и повтор `set` отсутствуют.

`SetExecution` проверяется непосредственно перед вызовом `write`. Просроченная или отменённая до начала запись не выполняется.
После начала записи ошибка драйвера даёт `outcome_unknown`, в том числе при `Synchronized`, сохраняя прежнюю консервативную семантику.
Таймаут ожидания клиентом не освобождает порт: worker ждёт завершения вызова. Доступный результат имеет приоритет над таймаутом,
а поздний ответ не создаёт второй окончательный результат `Pending`.

Очереди команд и наблюдений ограничены; каждый ответ имеет отдельный канал ёмкостью 1.
При заполнении очереди наблюдений новое наблюдение отбрасывается без ожидания, опрос и `get`/`set` продолжаются.
Каждая такая потеря увеличивает атомарный счётчик `PortHandle::loss_epoch()`, отдельный для каждого worker.
Чтение счётчика не захватывает блокировку управления и не зависит от заполненности очереди; освобождение очереди его не сбрасывает.
При достижении `u64::MAX` счётчик насыщается вместо переполнения: это постоянный признак потерь с неизвестной дальнейшей непрерывностью.

Будущий агрегатор должен сохранять последнее значение счётчика (для нового worker — 0), проверять его до и после чтения порций наблюдений,
а также после опустошения или закрытия очереди. Изменение означает разрыв потока; `u64::MAX` всегда означает неизвестную непрерывность.
Успешно помещённые в очередь наблюдения сохраняют FIFO-порядок, но могут находиться как до, так и после потери.
Счётчик не содержит позиции разрыва или идентификатора потерянного сигнала; точную границу между соседними наблюдениями он не гарантирует.
Отказ `try_send` и увеличение счётчика — отдельные операции: конкурентный читатель может заметить потерю при следующей проверке.
Равенство двух снимков счётчика не является атомарным подтверждением целостности прочитанной порции. Потерянные наблюдения не воспроизводятся.

Отключение получателя наблюдений по-прежнему завершает worker с `ObservationReceiverDropped`; это отдельное событие, не увеличение счётчика переполнений.
Причина остановки доступна через результат `run()` и `PortHandle::stop_reason()`; EOF наблюдений сам по себе не означает отсутствие потерь.
Ошибки и раскручиваемые panic драйвера изолированы данным worker; другие порты продолжают работу.

Ограничения: восстановление синхронизации не реализовано, совместимость протоколов не определяется.
Worker доверяет контракту драйвера о завершении транзакции; он не может самостоятельно проверить чужой формат ответа.
Текущий синхронный интерфейс не позволяет прервать зависший драйвер: драйвер/I/O обязан иметь конечные таймауты.
Изоляция panic не распространяется на завершение всего процесса (`panic=abort` и аналогичные сбои).
Прежний runtime пока лишь преобразует типизированные ошибки обратно в текст; политика остановки общего порта относится к новому worker.

## DeviceRegistry и CommandRouter (этап 3C1)

`lab_server::device_registry` и `lab_server::command_router` — самостоятельные компоненты library.
Подключение к TCP реализовано адаптером этапа 3C3 ниже; модуль `startup` собирает эти компоненты из TOML.
Имена сигналов и команды существующего Arduino/TCP runtime остаются прежними.

`DeviceRegistry` хранит физические порты, логические приборы и точный индекс глобальных ключей
`device_id/local_parameter`, например `furnace1/power` и `gauge1/temperature`.
У разных приборов могут совпадать локальные имена; коротких псевдонимов нет.
`device_id` не может быть пустым или содержать `/`. Локальное имя не разбирается и не нормализуется:
например, локальный `nested/value` у прибора `gauge1` даёт ключ `gauge1/nested/value`.

Основной API реестра:

- `DeviceRegistry::new()`; `register_port(port_id, PortHandle)` регистрирует один handle на физический порт.
- `register_unavailable_port(port_id, reason)` сохраняет порт, который не удалось открыть или запустить, и текст причины.
- `register_device(port_id, &DeviceInstance)` копирует проверенный каталог прибора, включая настроенные периоды опроса.
  Повторные идентификаторы портов/приборов и ссылка на незарегистрированный порт возвращают `RegistryError`.
- `port(id)`, `device(id)`, `parameter(global_key)` и итераторы `ports()`, `devices()`, `parameters()` дают доступ только для чтения.
  `RegisteredParameter` содержит `global_key`, `device_id`, `port_id` и существующий `ParameterDescription`;
  в `description.id` сохранено локальное имя драйвера, а в `spec`, `unit`, `writable`, `default_poll_period` — исходные свойства.
- `availability(device_id)` возвращает `Option<Availability>`; неизвестный прибор даёт `None`.
  `RegisteredPort::availability()` вычисляет тот же статус непосредственно для порта.
- `observation_parameter(&DeviceObservation)` сопоставляет точную пару `(device_id, Observation.source)` с записью глобального каталога.
- `RegisteredPort::handle()` и `loss_epoch()` доступны и после остановки; для порта без worker оба возвращают `None`.

Доступность представлена `Availability::Available`, `Unavailable { reason: String }` и `Stopped { reason: StopReason }`.
Для зарегистрированного handle состояние вычисляется по `PortHandle::stop_reason()` при каждом обращении.
Это снимок состояния, который может измениться сразу после чтения; отдельной копии статуса worker нет.
При явном `shutdown` handle закрывает приём команд сразу, хотя текущая операция ещё может завершаться.
Все приборы общего порта видят одну причину остановки. Другие порты продолжают работу.
Каталог недоступного или остановленного прибора сохраняется целиком.

Сначала нужно настроить периоды `DeviceInstance::set_poll_period`, затем создать worker и зарегистрировать
именно его экземпляры через read-only `PortWorker::devices()`. `DeviceInstance::id()` и `parameters()`
позволяют читать этот каталог без повторного вызова драйвера. Пример сборки из уже подготовленных `io` и `devices`:

```rust
let (worker, channels) = PortWorker::new(io, devices, 32, 128)?;
let mut registry = DeviceRegistry::new();
registry.register_port("shared_bus", channels.commands.clone())?;
for device in worker.devices() {
    registry.register_device("shared_bus", device)?;
}
registry.register_unavailable_port("offline_link", "COM4: access denied")?;
registry.register_device("offline_link", &offline_device)?;
let router = CommandRouter::new(registry);
let worker_thread = std::thread::spawn(move || worker.run());
// Владелец системы сохраняет channels.observations и управляет shutdown/join.
let pending = router.read(1, "gauge1/temperature", deadline)?;
```

Регистрация не открывает порт и не запускает поток. Вызывающий код отвечает за соответствие handle,
физического порта и переданных worker приборов, запуск `run()` и сохранение приёмника наблюдений.
Для недоступного порта каталог можно получить из созданного `DeviceInstance` без какого-либо I/O.
Драйверы общего порта могут совпадать или различаться; реестр не проверяет совместимость протоколов.

`CommandRouter::new(registry)` принимает готовый реестр; клоны router разделяют один неизменяемый каталог через `Arc`.
`registry()` предоставляет доступ к нему. `description(global_key)` ищет описание,
`availability(device_id)` — доступность, с явной ошибкой для неизвестного прибора.
`read(id, global_key, deadline)` и `set(id, global_key, value, deadline)` находят прибор и порт,
передают только локальное имя в `PortHandle` и сразу возвращают исходный `Pending`.
Маршрутизация не ожидает физического ответа или свободного места в очереди, не создаёт поток ожидания
и не добавляет очередь поверх ограниченной очереди порта. Потоки приложения могут использовать клоны router конкурентно.

Ошибки при приёме команды представлены `RouteError`: `UnknownSignal`, `UnknownDevice` (при запросе доступности),
`Unavailable` с текстовой причиной, `Stopped` с исходным `StopReason`, `QueueFull` с идентификатором порта,
`ReadOnly` и `InvalidValue` с глобальным ключом. Проверка записи выполняется до помещения в очередь;
worker повторно проверяет её по своему каталогу. Boolean не преобразуется в число, числовые диапазоны сохраняются.
Остановку при отправке проверяет сам `PortHandle` под существующей блокировкой приёма команд,
поэтому предварительный снимок `Available` не является обещанием принять следующую команду.

Принятая операция сохраняет прежние типы результата:
`Pending<Result<DeviceObservation, CommandError>>` для чтения и `Pending<Result<(), CommandError>>` для записи.
Ошибка физического чтения остаётся в `Observation.reading`; отказ ожидающей операции — в `CommandError`.
`Observation.source` остаётся локальным; публичный глобальный ключ определяется через каталог.
Идентификатор запроса и дедлайн проходят без изменений. Router не меняет `SetExecution`:
таймаут/отмена до начала исключает вызов записи драйвера, неопределённый результат начатой записи сохраняется
как `CommandError::OutcomeUnknown` либо `Completion::OutcomeUnknown` при опросе `Pending`.
Автоматических повторов нет. `Pending::poll` потребляет завершённый запрос; удаление `Pending` само по себе не отменяет запись.

Для этапа 3C2 доступны отдельные счётчики потерь через `registry.port(port_id).loss_epoch()`.
Будущий агрегатор должен связывать каждый приёмник с его портом, сверять `RegisteredParameter::port_id`
при сопоставлении наблюдения и отслеживать счётчик отдельно для каждого порта по правилам этапа 3B выше.
Реестр не объединяет потоки, не определяет точную позицию потери и не восстанавливает пропущенные наблюдения.
Сохраняются ограничения синхронного драйвера и восстановления синхронизации из этапа 3B.
Создание драйверов по имени, жизненный цикл частичного запуска, открытие портов, TCP-маршрутизация
и переподключение остаются задачами следующих этапов.

## Агрегатор наблюдений (этап 3C2)

`lab_server::observation_aggregator::ObservationAggregator` объединяет наблюдения выбранных физических портов.
Сам компонент не зависит от TCP и `main`; не открывает соединений, не создаёт драйверов или потоков.
Он заимствует неизменяемый `DeviceRegistry` и принимает пары `(port_id, Receiver<DeviceObservation>)`:

```rust
let mut aggregator = ObservationAggregator::new(
    router.registry(),
    vec![
        ("arduino_link".into(), arduino_observations),
        ("shared_bus".into(), shared_observations),
    ],
)?;
let events = aggregator.poll(8);
let finished = aggregator.is_finished();
```

На один физический порт передаётся ровно один приёмник, независимо от числа его приборов.
Можно выбрать подмножество зарегистрированных портов. Неизвестный порт, повторный приёмник порта
или порт без worker дают `BuildError`. Недоступные при запуске порты сохраняются в реестре без фиктивных источников.
Для уже остановленного worker можно передать его оставшийся приёмник и дочитать очередь.
Вызывающая сторона отвечает за соответствие приёмника реальному worker: `std::mpsc` не предоставляет идентификатора отправителя.
Каждое наблюдение дополнительно проверяется по принадлежности прибора данному порту и точному индексу параметров реестра.

Типизированные события `AggregatorEvent`:

- `Measurement { port_id, global_key, observation }` — глобальное имя из реестра и исходный `Observation`.
  Локальный `source`, время, единица, тип Integer/Float/Boolean и ошибка чтения сохраняются без изменений.
- `DataLost { port_id, loss_epoch }` — изменение счётчика потерь конкретного физического порта.
- `PortStopped { port_id, reason }` — закрытие источника с исходным `StopReason`.
- `InvalidObservation { port_id, observation, error }` — неизвестный прибор, неизвестный параметр
  или прибор другого порта (`MappingError::WrongPort` содержит зарегистрированный порт).
  Такое наблюдение не выдаётся как `Measurement`.
- `SourceClosedWithoutStop { port_id }` — приёмник закрылся, но у соответствующего handle нет причины остановки.
  Это нарушение привязки источника/жизненного цикла; агрегатор не подменяет его фиктивным `Shutdown`.

`poll(max_sources)` делает один проход по не более чем `min(max_sources, число активных источников)` портам,
по кругу, извлекая не более одного наблюдения с каждого. Пустой порт тоже расходует один шаг.
Максимум результата — два события на посещённый порт; бюджет 0 не выполняет работу.
Один загруженный порт не вытесняет остальные, а множество пустых портов не вызывает неограниченного поиска.
Внутренней очереди измерений или событий нет; источники читаются через `try_recv` без ожидания данных.
Внешний цикл сам выбирает частоту вызовов и ожидание между ними. Пустой результат не равнозначен завершению.

Для каждого порта независимо хранится последнее сообщённое значение `loss_epoch`, начиная с 0.
При каждом посещении счётчик читается **до и после** `try_recv`, включая пустую и закрытую очередь.
Если он вырос, возвращается одно `DataLost` с последним увиденным значением, перед событием наблюдения этого посещения.
Несколько потерь могут объединяться в одно уведомление. Потери, случившиеся до создания агрегатора,
также обнаруживаются, даже если очередь уже прочитана. Чтение очереди и отправка уведомления не сбрасывают счётчик.

**Порядок `DataLost` и `Measurement` не задаёт положение разрыва.** Успешно принятые наблюдения сохраняются,
но могут относиться к обеим сторонам потери. Изменение счётчика, обнаруженное после извлечения наблюдения,
сообщается в той же порции. Если worker увеличил счётчик позже второй проверки, уведомление придёт при следующем посещении,
в том числе при пустой очереди. Поэтому потребитель должен считать нарушенной непрерывность потока этого порта,
включая ранее выданные порции, и не считать измерения после `DataLost` автоматически началом непрерывного участка.
Равенство снимков не доказывает целостность порции. Другие порты этим уведомлением не затрагиваются.
При `u64::MAX` выдаётся уведомление о насыщении; неизвестная непрерывность остаётся постоянной до конца жизни источника.
Повторных одинаковых уведомлений нет, и отсутствие новых уведомлений после насыщения не означает восстановление.
Недостающие точки не восстанавливаются; команды PortWorker продолжают исполняться независимо от потерь.

`PortStopped` выдаётся один раз после опустошения очереди, обнаружения EOF и последней проверки счётчика.
У корректно привязанного worker после закрытия его отправителя новых изменений счётчика уже быть не может.
Накопленные измерения данного порта сохраняют FIFO-порядок и предшествуют событию остановки;
между разными портами временная сортировка не выполняется. EOF не доказывает отсутствие потерь.
`Desynchronized`, `Disconnected`, штатный `Shutdown` и другие причины сохраняются без преобразования.
Обычная ошибка измерения при `Synchronized` остаётся в `Observation.reading` и не закрывает источник.
Остановка одного порта не мешает дальнейшей обработке остальных. `is_finished()` становится `true`,
когда для всех выбранных источников возвращены терминальные события; без источников оно сразу `true`.

Владение приёмниками передаётся агрегатору. Его удаление, в том числе при ошибке создания, закрывает переданные приёмники:
сохраняется действующая политика PortWorker `ObservationReceiverDropped`.
Агрегатор не прерывает зависший драйвер и не считает один только закрытый приём команд доказательством EOF.
Перевод потерь порта в уведомления TCP-подписчикам реализован в этапе 3C3 ниже.
Сам агрегатор остаётся независимым от TCP JSON и подписок.

## TCP с несколькими приборами (этап 3C3)

`lab_server::tcp::MultiDeviceTcp` связывает `CommandRouter`, `DeviceRegistry` и `ObservationAggregator`
с существующими `ClientSession`, `TcpConnection` и `ObservationFanout`.
Один endpoint может обслуживать несколько PortWorker и несколько приборов с разными драйверами на общем порту.
TCP, fanout, протокол и прежний runtime теперь объявлены в library; binary использует те же реализации и типы.
В `main` сохранены Arduino, `COM3`, 57600 бод, прежние локальные ключи и прежний runtime.
При запуске по TOML модуль `startup` передаёт backend созданный реестр и запускает workers.

Публичный API:

- `MultiDeviceTcp::new(router, observation_capacity)` создаёт каталог глобальных ключей, кеш и fanout.
  Ёмкость персональной очереди наблюдений положительна и ограничена.
- `registry()` возвращает неизменяемый реестр для создания агрегатора.
- `collect(&mut aggregator, max_sources)` обрабатывает ограниченную порцию событий в порядке агрегатора.
  `apply_event(event)` позволяет внешнему циклу последовательно передавать уже полученные события.
- `serve_connection(TcpStream)` запускает прежний TCP-цикл с новым backend для одного принятого соединения:
  максимум 64 pending-запроса, 64 KiB выходного буфера, дедлайн команды 10 секунд.
- Для внешнего цикла доступны `register_client()` и `drive_connection(&mut TcpConnection, &ObservationReceiver)`.
  Отдельных потоков ожидания команд или новых очередей команд нет.

Владелец listener должен удерживать `ClientSlots` permit на каждое соединение (действующий предел — 32 клиента).
Отдельно он вызывает `collect`, сохраняет приёмники агрегатора и управляет shutdown/join worker.
Минимальная последовательность сборки из уже подготовленных объектов:

```rust
let server = Arc::new(MultiDeviceTcp::new(CommandRouter::new(registry), 128));
let mut aggregator = ObservationAggregator::new(server.registry(), receivers)?;
// Цикл listener передаёт принятые сокеты в server.serve_connection(stream),
// сохраняя ClientSlots permit до завершения обработки каждого клиента.
// Внешний цикл наблюдений выполняет ограниченную работу и затем уступает CPU:
server.collect(&mut aggregator, 8)?;
```

Новый режим использует точные публичные ключи `device_id/local_parameter`, включая `/` внутри локальной части.
`describe` включает недоступные и остановленные приборы, исходные типы, диапазоны и периоды опроса.
Для периодического `get` используется кеш либо `no_data`. Перед чтением кеша проверяется доступность порта;
при остановке возвращается `runtime_unavailable`, даже до получения агрегатором EOF.
При обработке закрытия источника его кеш удаляется. Непериодические `get` и все `set` передаются через router.
Результаты чтения и события получают глобальный ключ; значения Integer/Float/Boolean не преобразуются,
`i64` сериализуется точно, время и поля измерения сохраняют прежнее представление JSON v1.

Ошибки отображаются в действующие коды:

| Внутренняя ошибка | TCP |
| --- | --- |
| Неизвестный глобальный ключ | `unknown_key` |
| Недоступный или остановленный порт | `runtime_unavailable` |
| Заполненная очередь PortWorker | `runtime_busy` |
| Заполненный список pending | `too_many_pending` |
| Только чтение / неподходящий тип или диапазон | `Parameter is read-only` / `Value does not match parameter spec` |
| Не начавшаяся запись с истёкшим дедлайном | `runtime_timeout` |
| Неопределённый результат начавшейся записи | `outcome_unknown` |

Router передаёт исходный `Pending` вместе с его `SetExecution`; TCP не создаёт для него второй механизм исполнения.
Дедлайн охватывает ожидание в очереди. Отмена запрещает исполнение записи, но её слот освобождается
только после извлечения команды worker. У запроса остаётся не более одного окончательного ответа;
поздний ответ после таймаута/`outcome_unknown` не публикуется повторно. Автоматических повторов записи нет.
Порядок ответов может отличаться от порядка запросов, а request ID по-прежнему должны возрастать.

В новом fanout ключи фильтруются **до помещения** в единственную ограниченную очередь клиента.
Для каждой активной подписки на физический порт хранится исходный счётчик потерь; несколько ключей одного порта
используют одну границу. Потеря на A закрывает только TCP-потоки, подписанные на A во время потери.
Смешанная подписка A+B закрывается целиком с `observation_data_lost`; подписка только B продолжает работу.
Персональное переполнение сохраняет прежний порядок: уже помещённый префикс очереди, затем ошибка потери.
Клиенты без подписок продолжают выполнять команды независимо от потерь наблюдений.

Граница подписки согласована с физической публикацией: worker защищает короткой блокировкой
`try_send` и фиксацию `Full` в `loss_epoch`. Изменение подписки использует ту же границу;
для нескольких затронутых портов блокировки берутся в порядке идентификаторов.
Они не удерживаются во время вызова драйвера, COM-I/O, TCP-I/O или ожидания места в очереди.
При отписке сначала фиксируются потери старого активного интервала. Этот признак сохраняется до закрытия TCP,
включая удаление всех подписок и повторную подписку до обработки уведомления.

Проверка использует непосредственно счётчик PortHandle, поэтому задержка агрегатора не скрывает потерю.
Потеря до первого включения подписки входит в её исходный снимок и не вызывает ошибку;
запоздавший `DataLost` с уже учтённым значением также не закрывает новую подписку.
При `u64::MAX` счётчик больше не доказывает непрерывность: даже новая подписка завершается `observation_data_lost`.
Положение разрыва остаётся неизвестным. ACK по-прежнему предшествует новым событиям подписки;
граница исключения старых публикаций относится к публикации в fanout, а не к времени физического измерения.

`PortStopped` и `SourceClosedWithoutStop` закрывают подписанные на этот порт TCP-потоки с
`observation_stream_closed`, сохраняя уже помещённый префикс. При наличии потери приоритет имеет `observation_data_lost`.
Причина PortStopped сохраняется в PortHandle/реестре и диагностике; JSON новых полей причины не добавляет.
`InvalidObservation` выводится в диагностику и необратимо помечает поток этого порта повреждённым:
его подписчики получают `observation_data_lost`, новые подписки на повреждённый поток также завершаются.
Другие порты продолжают работу. Этот признак не меняет физическое состояние worker и не запускает переподключение.
Восстановление потока требует нового backend/источника; hot reload и автоматического восстановления пока нет.

`hello.version = 1`, набор команд, форматы JSON и фактический запуск Arduino сохранены.
Новый backend проверяется через реальные loopback TCP-соединения с имитационными DeviceIo и драйверами;
Arduino и COM-порты в этих тестах не открываются.

## Формат обмена

TCP, NDJSON, UTF-8: одно JSON-сообщение на строку, завершённую LF (`\n`).
Сообщение — JSON-объект; имена полей не должны повторяться. Максимальный размер входного кадра — **16 KiB без LF**.
Границы чтений из TCP не совпадают с границами сообщений: клиент должен собирать строки до LF.

- Каждый запрос содержит `id` и строковое поле `op`.
- `id` — положительное целое `u64` (1…18446744073709551615), строго возрастающее в пределах соединения.
  Даже отклонённая команда расходует корректный новый ID; некорректный JSON, повторные поля и неверный ID — нет.
  Перед исчерпанием диапазона нужно открыть новое соединение.
- Повторный или меньший ID вызывает `duplicate_id` **без поля `id`**; исходный pending-запрос сохраняется.
- Ответы сопоставляются с запросами по `id`. Асинхронные события `measurement` не имеют `id`.
  Ответы и события могут чередоваться; порядок ответов не обязан совпадать с порядком запросов.

## Команды

Обязательные для всех команд поля — `id` и `op`; дополнительные поля указаны в таблице.
JSON-примеры запросов нужно отправлять с завершающим LF. Примеры ответов предполагают указанные ID.

| `op` и назначение | Дополнительные обязательные поля | Пример запроса | Успешный ответ |
| --- | --- | --- | --- |
| `hello` — версия протокола | — | `{"id":1,"op":"hello"}` | `{"id":1,"status":"ok","protocol":"lab-server","version":1}` |
| `describe` — каталог параметров | — | `{"id":2,"op":"describe"}` | `id`, `status: "ok"`, массив `parameters` |
| `ping` — проверка связи | — | `{"id":3,"op":"ping"}` | `{"id":3,"status":"ok"}` |
| `get` — получить значение | `key`: строка | `{"id":4,"op":"get","key":"heater_temperature"}` | `id`, `status: "ok"`, `key`, `value`, `unit`, `completed_at_unix_ms` |
| `set` — записать значение | `key`: строка, `value`: число или Boolean | `{"id":5,"op":"set","key":"power","value":20}` | `{"id":5,"status":"ok"}` |
| `subscribe` — добавить подписки | `keys`: массив строк; либо одиночный `key` | `{"id":6,"op":"subscribe","keys":["heater_temperature"]}` | `{"id":6,"status":"ok","keys":["heater_temperature"]}` при отсутствии других подписок |
| `unsubscribe` — удалить подписки | `keys`: массив строк | `{"id":7,"op":"unsubscribe","keys":["heater_temperature"]}` | `{"id":7,"status":"ok","keys":[]}` при удалении последней подписки |

### Каталог и значения

В `describe.parameters` каждый объект содержит `key`, `type`, `min`, `max`, `unit`, `writable`, `poll_period_ns`.
`type` принимает `integer`, `float` или `boolean`. Для числовых типов границы `min` и `max` включительны.
Для `boolean`: `min: null`, `max: null`, `unit: ""`; оба значения `true` и `false` допустимы без числовых ограничений.
`poll_period_ns` — период опроса в наносекундах, либо `null`, если периодического опроса нет.
Например, элемент каталога для `power` (это фрагмент ответа `describe`):

```json
{"key":"power","type":"integer","min":0,"max":100,"unit":"%","writable":true,"poll_period_ns":1000000000}
```

Пример булевых параметров имитационного драйвера (они не входят в каталог Arduino):

```json
{"key":"enabled","type":"boolean","min":null,"max":null,"unit":"","writable":true,"poll_period_ns":null}
{"key":"fault","type":"boolean","min":null,"max":null,"unit":"","writable":false,"poll_period_ns":10000000}
```

Текущий каталог Arduino; у всех параметров период опроса — 1 с (`1000000000` нс):

| `key` | `type` | Диапазон | `unit` | `writable` |
| --- | --- | --- | --- | --- |
| `sample_temperature` | `float` | −250…1500 | `degC` | `false` |
| `heater_temperature` | `float` | −250…1500 | `degC` | `false` |
| `room_temperature` | `float` | −250…1500 | `degC` | `false` |
| `power` | `integer` | 0…100 | `%` | `true` |

Для `set` литералы `20` и `20.0` различаются: первый — `integer`, второй — `float`.
Запись требует `writable: true` и соответствия типу и диапазону; `20.0` для `power` будет отклонено.
Экспоненциальная запись также считается `float`; бесконечные значения и целые за пределами `i64` не принимаются.
Boolean передаётся JSON-литералами `true` и `false`, без кавычек. Неявных преобразований между Boolean и числами нет:
для булевого параметра `1`, `0`, `1.0`, `0.0` и строка `"true"` отклоняются до обращения к драйверу;
для числового параметра `true` и `false` также недопустимы. Например, запросы к имитационному драйверу:

```json
{"id":8,"op":"set","key":"enabled","value":true}
{"id":9,"op":"set","key":"enabled","value":false}
```

Успешный ответ `set` остаётся ACK с `id` и `status: "ok"`. Правила таймаута и `outcome_unknown` одинаковы для всех типов.

`get` периодически опрашиваемого параметра возвращает последнее измерение, включая последнюю ошибку чтения.
Если измерений ещё нет, ответ имеет `status: "no_data"`. Для параметра без периодического опроса выполняется отдельное чтение.
Варианты ответа на `get` (альтернативы, не несколько ответов на один запрос):

```json
{"id":4,"status":"ok","key":"heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"id":4,"status":"no_data","key":"heater_temperature"}
{"id":4,"status":"error","key":"heater_temperature","error":"Empty response","completed_at_unix_ms":1700000000000}
```

Успешный `get` булевого параметра возвращает JSON Boolean, а не число или строку; `unit` всегда пустая строка.
Например, после записи `enabled` в имитационном драйвере:

```json
{"id":10,"op":"get","key":"enabled"}
{"id":10,"status":"ok","key":"enabled","value":false,"unit":"","completed_at_unix_ms":1700000000000}
```

### Подписки

Подписки индивидуальны для TCP-клиента. Подписаться можно только на периодически опрашиваемые параметры.
Повторное `subscribe` идемпотентно: оно добавляет ключи к текущему набору, а не заменяет его.
`subscribe` также принимает `{"id":8,"op":"subscribe","key":"heater_temperature"}`; одновременно `key` и `keys` передавать нельзя.
`unsubscribe` принимает только `keys`, без одиночного `key`. Пустой `keys: []` ничего не изменяет, в том числе не удаляет все подписки.
Дубликаты ключей удаляются. Успешный ответ обеих команд содержит актуальный полный список `keys`, отсортированный по имени.
Изменение набора атомарно: неизвестный или неподписываемый ключ приводит к отказу всего запроса.

## Асинхронные события

Примеры успешного измерения и ошибки чтения:

```json
{"event":"measurement","status":"ok","key":"heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"event":"measurement","status":"error","key":"heater_temperature","error":"Empty response","completed_at_unix_ms":1700000001000}
```

Для булевого параметра `value` — JSON Boolean, `unit` — пустая строка. Примеры событий `fault` имитационного драйвера:

```json
{"event":"measurement","status":"ok","key":"fault","value":true,"unit":"","completed_at_unix_ms":1700000000000}
{"event":"measurement","status":"ok","key":"fault","value":false,"unit":"","completed_at_unix_ms":1700000000010}
{"event":"measurement","status":"error","key":"fault","error":"simulated read failure","completed_at_unix_ms":1700000000020}
```

Добавление Boolean не меняет версию протокола: `hello.version` остаётся `1`.

`completed_at_unix_ms` — время завершения измерения в миллисекундах от Unix epoch, а не время отправки клиенту.
При ошибке чтения вместо `value` и `unit` передаётся строка `error`; поля `id` у событий нет в обоих случаях.
ACK (`status: "ok"`) для `subscribe` предшествует событиям новых подписок; публикации до их активации не воспроизводятся.
События следуют порядку публикации. После ACK `unsubscribe` новые измерения удалённого ключа не приходят;
уже поставленные в отправку события могут предшествовать ACK. Переподключение не восстанавливает пропущенные наблюдения.

## Ошибки и ограничения

Ошибка запроса обычно имеет поля `id`, `status: "error"`, `error`; для ошибки конкретного ключа может присутствовать `key`.
Если ID нельзя однозначно извлечь, он отсутствует. `duplicate_id`, ошибки кадра и завершения потока приходят без `id`.
Например: `{"status":"error","error":"duplicate_id"}` или `{"status":"error","error":"observation_data_lost"}`.

| Группа | Значения `error` и смысл |
| --- | --- |
| Кадр | `empty_frame`, `frame_too_long`, `invalid_utf8`, `incomplete_frame` (EOF до LF); соединение завершается |
| JSON | `invalid_json`, `expected_object`, `duplicate_key` |
| Поля запроса | `invalid_id`, `unsupported_op`, `invalid_key`, `invalid_value`, `invalid_keys` — неверное или отсутствующее поле |
| Уникальность ID | `duplicate_id` — повторный или меньший ID |
| Параметр и запись | `unknown_key`; `Parameter is read-only`; `Value does not match parameter spec` |
| Подписки | `not_subscribable` — нет периодического опроса; `too_many_subscriptions` — превышен лимит |
| Очереди | `too_many_pending` — лимит ожидающих запросов клиента; `runtime_busy` — очередь команд заполнена; `runtime_unavailable` — runtime недоступен |
| Ожидание | `runtime_timeout`, `outcome_unknown` — различия для `set` описаны ниже |
| Поток наблюдений | `observation_data_lost` — потеря данных; `observation_stream_closed` — закрытие без обнаруженного переполнения |

Ошибки чтения содержат текст драйвера или ввода-вывода, например `Empty response`; это не закрытый перечень кодов.
Ожидание `set` и отдельного чтения `get` ограничено 10 с, включая очередь. Для `set`:

- `runtime_timeout`: исполнение не началось; просроченная команда не будет отправлена устройству.
- `outcome_unknown`: исполнение началось, но результат неизвестен из-за таймаута, потери ответа или ошибки драйвера. **Автоматически повторять операцию нельзя.**
- Уже доступный результат имеет приоритет над таймаутом; поздний результат не порождает второго ответа.

При переполнении общей или персональной очереди наблюдений подписчик получает `observation_data_lost`, и повреждённый поток завершается.
После этого нужно новое соединение и новая подписка. Потеря при активной подписке не сбрасывается через `unsubscribe` → `subscribe` до уведомления.
Потеря в период без подписок не мешает последующей подписке; клиенты без подписок сохраняют соединение и pending-команды.
Переполнение выходного буфера или транспортная ошибка могут привести к закрытию без сообщения об ошибке.
EOF не доказывает полноту доставки измерений или неисполнение ожидающего `set`.

| Ресурс | Лимит |
| --- | --- |
| Одновременные TCP-клиенты | 32; лишние соединения закрываются |
| Pending-запросы на клиента | 64 |
| Подписки на клиента | 64 ключа |
| Выходной буфер клиента | 64 KiB |
| Очереди команд и наблюдений runtime | По 128 элементов |
| Персональная очередь наблюдений | 128 элементов |
