# Диагностика lab-server

`server_status` — дополнительная read-only операция протокола версии 1.
TCP: один JSON с LF; WebSocket: один Text message через существующий endpoint
`/application/v1`. Оба транспорта используют общий parser, dispatcher и снимок
`DeviceService`. Правила `id`, ошибок и ограничений соединения остаются прежними.

```json
{"id":10,"op":"server_status"}
```

Полный пример ответа при работающих портах, компонентах и Recorder:

```json
{
  "id": 10,
  "status": "ok",
  "data": {
    "server": {
      "state": "running",
      "error": null,
      "uptime_ms": 123456,
      "active_clients": 2,
      "listeners": {
        "tcp": {"state": "accepting", "address": "127.0.0.1:7240", "error": null},
        "websocket": {"state": "accepting", "address": "127.0.0.1:7241", "error": null}
      }
    },
    "ports": [
      {
        "id": "arduino",
        "state": "available",
        "reason": null,
        "loss_epoch": 0,
        "last_success_unix_ms": 1794902400000
      }
    ],
    "devices": [
      {"id": "furnace1", "port": "arduino", "state": "available", "reason": null}
    ],
    "processing": [
      {"name": "loop", "type_id": "pid", "state": "shadow", "error": null},
      {"name": "smooth", "type_id": "ema", "state": "running", "error": null}
    ],
    "recorder": {
      "enabled": true,
      "state": "running",
      "session_id": 12,
      "losses": {
        "dropped_events": 0,
        "dropped_data_lost_events": 0,
        "rejected_invalid_data": 0
      },
      "error": null
    }
  }
}
```

Массивы портов, приборов и компонентов отсортированы по идентификатору/имени.
Если элементов нет, возвращается `[]`. Конфигурация компонентов, коэффициенты,
привязки и ревизия остаются в `components/list`, сюда они не дублируются.

## Сервер и listeners

`server.state` — жизненный цикл: `ready` (подготовлен), `running` (обслуживает),
`stopping` (останавливается), `stopped` (владельцы ресурсов уничтожены).
Это не оценка исправности: сервер может оставаться `running` при недоступном порте
или `recorder.state: "failed"`. Общего поля `healthy` нет.
`server.error` содержит известную причину завершения/ошибку остановки либо `null`;
ошибки подсистем нужно смотреть в их собственных разделах.

`uptime_ms` — монотонное время с начала подготовки сервера, включая открытие
ресурсов; после завершения остановки фиксируется. `active_clients` — число
занятых разрешений существующего общего лимитера TCP/WS: включает текущее
соединение, незавершённые WS handshakes и закрывающиеся соединения до освобождения
разрешения. Не включает сокеты, ещё не принятые из системного backlog.

Состояния listener:

| `state` | Значение |
| --- | --- |
| `disabled` | Транспорт выключен; `address` и `error` равны `null` |
| `bound` | Сокет привязан, цикл обслуживания ещё не запущен |
| `accepting` | Цикл принимает соединения |
| `not_accepting` | Остановка началась, новые соединения не принимаются |
| `closed` | Владелец сокета уничтожен |
| `failed` | Зафиксирована фатальная ошибка accept; причина в `error`, сохраняется после остановки |

`address` — фактический адрес привязки, включая выделенный ОС порт при `bind: ...:0`.
Ошибка bind или открытия обязательного Recorder прерывает запуск: запросить статус
несуществующего сервера невозможно, причина доступна в ошибке запуска/stderr.
Обычно клиент видит `running`; финальный снимок можно получить через сохранённый
`DeviceService` в библиотечном API после остановки. Он не требует открытого сокета.

## Порты, приборы и обработка

Доступность читается из `DeviceRegistry` и его `PortHandle`:

- `available`: зарегистрированный worker не имеет причины остановки;
- `unavailable`: порт не удалось открыть; `reason` содержит ошибку открытия;
- `stopped`: handle хранит причину остановки worker, например `Shutdown`,
  ошибку драйвера или разрыв источника. `reason` — диагностический текст,
  его внутренний формат не предназначен для машинного разбора.

Доступность прибора наследуется от его порта. Это **не** отдельная проверка связи
с каждым прибором: отдельные ошибки чтения не обязательно останавливают общий порт.
`available` не гарантирует свежих измерений или успешного следующего чтения.

`loss_epoch` — существующий накопительный счётчик наблюдений, отброшенных из-за
переполнения очереди PortWorker. Чтение статуса его не сбрасывает. При насыщении
`u64::MAX` дальнейшее число потерь неизвестно. Это не счётчик ошибок драйвера,
потерь Recorder или переполнений очередей отдельных клиентов.
У не запущенного порта счётчика нет: `null`, а не ноль.

`last_success_unix_ms` — время завершения последнего успешного, прошедшего
проверку типа/диапазона чтения любого параметра на этом порту, в миллисекундах Unix.
Учитываются периодические опросы и явные чтения через `get`; set/invoke_action
не обновляют его. Отметка записывается самим worker перед передачей наблюдения,
поэтому сохраняется при потере наблюдения в очереди, ошибках последующих чтений
и остановке. Это системное время, оно может измениться при коррекции часов.
До первого успешного чтения и при непредставимом Unix-времени возвращается `null`.

`processing` читает текущие состояния существующего Engine: `running`, `shadow`,
`auto`, `stopped`, `fault`. `error` содержит имеющуюся причину ошибки либо `null`.
Наличие ошибки и состояние следует учитывать отдельно: например, фильтр может
оставаться `running` с ошибкой входа. Запрос не вызывает tick, reset или reconfigure.

## SQLite Recorder

При выключенной записи весь раздел имеет вид:

```json
{"enabled":false,"state":"disabled","session_id":null,"losses":null,"error":null}
```

При включённой записи состояние берётся из существующего `RecorderHandle`:
`running`, `closing`, `stopped`, `failed`. `session_id` сохраняется и после ошибки
или завершения. `error` содержит причину `failed`, иначе `null`.
Запрос не открывает БД и не ждёт writer, flush или fsync.

Счётчики `losses` также читаются из handle:

- `dropped_events`: события, отклонённые из-за полной очереди Recorder;
- `dropped_data_lost_events`: **часть** `dropped_events`, состоящая из сообщений
  о потере в PortWorker; это не дополнительное число потерянных измерений;
- `rejected_invalid_data`: отклонённые невалидные данные, отдельно от переполнения.

Счётчики насыщаются на `u64::MAX`. Они не учитывают события, отклонённые после
закрытия/ошибки writer, и не подтверждают сохранность всех принятых записей при
ошибке SQLite. `failed` нельзя игнорировать даже при нулевых потерях.
Общий точный счётчик всех потерь и проверка целостности файла этим API не обещаются.

## Согласованность и границы

Снимок **не глобально атомарен**: lifecycle, лимитер клиентов, отдельные handles,
Engine и Recorder читаются независимо из памяти. Между чтениями порт может
остановиться, клиент отключиться или Recorder перейти в ошибку; допустимы небольшие
расхождения, в том числе между состоянием порта и его приборов.

Используются короткие блокировки существующих источников, атомарный счётчик
лимитера и одна короткая блокировка новой отметки времени в PortHandle, вне I/O.
Новый runtime-контекст хранит только время запуска/lifecycle/listeners и ссылки
на существующие лимитер и Recorder. Параллельной модели портов/компонентов нет.
В библиотечном `DeviceService`, созданном без `start_with`/`start`, неизвестные
`server` и `recorder` равны `null`; сетевой сервер всегда устанавливает runtime.

Чтение не меняет контроллеры, владение выходами, подписки, очереди наблюдений
или конфигурацию. Меняется только обычное состояние запроса в клиентской сессии
(ID и очередь ответа). Существующие ограничения отправки медленным клиентам действуют.
Размер снимка ограничен бюджетом 48 КиБ содержимого; слишком большой снимок
возвращает `{"id":10,"status":"error","error":"status_too_large"}` без частичных
списков. Пагинации диагностики нет. Это ограничивает работу под блокировкой
существующего диспетчера и оставляет место в стандартном выходном буфере 64 КиБ.

## Сообщения stderr

Сохраняются сообщения о недоступном порте с его ID и причиной, завершении worker
и отказе Recorder. Добавлены начало/завершение остановки сервера и предупреждение
о первой обнаруженной потере наблюдений для каждого порта (ID и `loss_epoch`).
Дальнейшие потери видны через `server_status`; предупреждения о переполнении
Recorder уже ограничены одним сообщением. На каждое измерение сообщений нет.
Новая система логирования и обращения к оборудованию для диагностики не вводятся.
