# Стоимость клиентских запросов Session

Эксперимент поверх `ce866340606c59369380aba3a8cd10de2fd84731`. Изменения
ограничены опциональным измерителем, тестами и стендом. Протокол, границы
`gate`, доступность, подписки и аудит используют прежние правила.

## Как читать фазы

| Метрика CSV | Граница |
| --- | --- |
| `parse` | `ParsedMessage::parse`, строгий JSON и распознавание операции. Для TCP начинается после выделения NDJSON-кадра, для WebSocket — после чтения текстового сообщения. |
| `dispatch` | Извлечение пригодного ID, проверка порядка, подготовка аудита и регистрация запроса до вызова обработчика. Последний выбор ветки обработчика остаётся между замерами. |
| `catalog` | Полный вызов `CommandBackend::catalog_snapshot`, включая захват mutex Engine. |
| `snapshot_build` | Вложенный вызов `Engine::catalog()` после захвата mutex в `DeviceService::catalog_snapshot`. |
| `get` | Обработчик `dispatch_get` целиком. Включает lookup каталога, mutex `latest`, availability, подготовку значения и очередь ответа. |
| `availability` | Вызов `CommandBackend::available` для существующего опрашиваемого ключа. |
| `availability_build` | `Engine::catalog()` после захвата mutex внутри производной ветки availability. Вложен в `availability`. |
| `get_value` | Поиск в уже захваченном `latest` и подготовка JSON-ответа со значением или `no_data`. |
| `actions` | `CommandBackend::actions()` для Describe. |
| `describe` | `describe_response`, включая построение и освобождение временных JSON-структур. Каталог, получение действий и очередь ответа находятся за его пределами. |
| `describe_sort` | Сбор ссылок на параметры и сортировка, затем отдельный замер сортировки действий. Два замера на Describe. |
| `describe_json` | Формирование массива параметров, затем массива действий и корневого объекта. Два замера на Describe. |
| `describe_serialize` | Сериализация готового объекта в строку. |
| `response` | `queue_response`, включая учёт ответа для аудита при необходимости и попытку поставить строку в ограниченную очередь. |

Для расчёта долей используются суммы времён внутри одного повтора.
Вложенные фазы не складываются с родительскими. Процентили разных фаз
не складываются и не вычитаются. Для сортировки и построения JSON
«мкс на запрос» получаются делением суммарного времени на число Describe,
а не на число сегментов. В строках CSV p50/p95/p99 относятся к одному
сегменту.

Feature `gate-metrics` включает опциональный сбор фаз. Стенд подключает
сборщик к потоку на время серии. Снимок берётся после завершения
потоков. У каждой фазы ограниченная гистограмма с восемью корзинами
на степень двойки, как у измерителя gate, плюс точные счётчик,
максимум и сумма измеренных длительностей. Верхняя граница корзины
округляет длинные интервалы вверх не более чем на 12,5%. Запись
атомарных агрегатов фазы выполняется на измеряемом пути и добавляет
накладные расходы в `hold`. Снимки, форматирование CSV и клиентская
проверка ответов идут вне `gate`. Обычная сборка компилируется без хуков.

## Воспроизведение

```powershell
$env:CARGO_TARGET_DIR = 'D:\rust_projects\lab-server-agent-build'
cargo run --release --locked --features gate-metrics --example service_gate_bench -- --session-request-phases > phases.csv
cargo run --release --locked --features gate-metrics --example service_gate_bench -- --session-request-calibration > calibration.csv
```

Windows 10 Pro 22H2 (19045), AMD Ryzen 5 6600H (6 ядер, 12 логических),
rustc 1.95.0 для `x86_64-pc-windows-msvc`, стандартный Release.
Пять отдельных повторов, свежий DeviceService на каждый. Цепочка из
1, 8, 32 или 128 EMA. Стенд использует имитационный PortWorker и передаёт
измерения на границе агрегатора, с идентичностью порта, монотонной
`sequence` и меткой acquisition. Сначала подаётся один образец,
затем восемь раундов прогрева. Статистика gate сбрасывается перед серией,
а Session или loopback-соединение создаются заново.

| Режим | Участники | Серия |
| --- | --- | --- |
| `solo` | Один клиент Session | 256 запросов |
| `producer` | Один клиент Session и производитель | 256 запросов и 256 измерений |
| `many` | Три клиента Session и один производитель | 768 запросов и 256 измерений |
| `tcp`, `websocket` | Один клиент и реальный серверный адаптер в отдельных потоках | 48 запросов через loopback без параллельных измерений |

В конкурентных прямых режимах Barrier выравнивает начало каждого
раунда. Отдельные нагрузки — Ping, физический и производный Get,
Get с известным, но пустым кешем, Get неизвестного ключа и Describe.
В раздельных нагрузках два физических ключа, один из которых
остаётся без значения, и два имитационных действия. `mixed`
сохраняет набор блока 5 с одним физическим ключом и без действий.
В `many` один клиент занят Ping, второй производным Get,
третий Describe. В режимах с одним клиентом запросы чередуются.

Для loopback измеряется Ping, производный Get и Describe. Время клиента
считается от отправки подготовленного запроса до чтения ответа целиком,
до проверки его содержимого. Оно включает транспорт, планировщик и
циклы сервера. TCP-метрики gate включают и пустые обороты, и работу с
сокетом. В WebSocket под gate проходят Parse и Session, чтение и
передача кадров идут отдельно. Замер не выделяет собственно сетевую
передачу из RTT. Loopback использует TCP_NODELAY, 2-мс паузы в штатных
серверных циклах и одно ожидающее сообщение на клиенте.

Стенд сверяет ID, статусы и данные, сортировку и набор Describe,
количество принятых образцов и актуальность конечного кеша. Размер
ответа — байты JSON без NDJSON-разделителя и обрамления WebSocket.
`--session-request-calibration` попарно повторяет solo для Ping,
производного Get и Describe на 1 и 128 узлах, чередуя порядок
с активным и неактивным сборщиком фаз. Замеры gate включены в обеих
версиях. Нет оборудования, активной записи SQLite,
подписчиков и перегрузки исходящей очереди в этих сценариях.

## Контракт Get

- `get` сначала получает снимок каталога и ищет описание ключа. Для
  неизвестного ключа возвращается `unknown_key` до захвата `latest`
  и до вызова availability. При `None` от backend используется
  переданный базовый каталог.
- Для опрашиваемого ключа `latest` захватывается **до** вызова
  `available`. У физического ключа проверяются реестр портов, признак
  непригодности fanout и живое состояние порта. При отказе возвращается
  `runtime_unavailable`, до чтения значения из кеша. При доступном
  ключе без записи возвращается `no_data`.
- Для производного ключа `DeviceService::available` проверяет текущую
  принадлежность каталогу Engine. Он не интерпретирует здоровье
  физического источника как недоступность производного ключа. Ошибка
  источника может появиться в самом кешированном наблюдении.
- Create добавляет ключ в текущий каталог. Configure со сменой входа
  очищает затронутую историю, пока следующее измерение не создаст новое
  значение. Delete убирает ключ. Эти случаи, остановка физического
  порта и `no_data` для производного сигнала проверены тестом.
- Пользовательский backend может сохранять собственную проверку
  доступности даже для ключа из снимка. Тест подтверждает вызов с
  удерживаемым `latest`, базовый каталог при `None` и точный `u64::MAX`.

### Get — каталоги и доступность

Учёт вызовов совпал во всех повторах, при любом числе узлов и
конкурентов. Ping, Hello и ошибочный JSON дают ноль построений.
`get_unknown_key` — одно построение и ноль вызовов availability.
Физический Get и исследованный физический `no_data` дают одно
построение и одну проверку availability. Производный Get даёт по
одному построению в двух местах, суммарно два. Это верно и для
известного производного ключа с пустым кешем в целевом тесте.

второе построение.

Ранний контроль с последовательными непарными сериями исключён

фаз при 128 узлах. Два каталога заняли 87,9% hold производного

86,6% и 79,9% соответственно. Доли и счётчики полезнее для выбора
следующего изменения, чем абсолютная разница между сериями.

## Предложения для следующего блока

1. **Сериализовать Describe напрямую.** Сохранить сортировку
   параметров и действий, но передавать заимствованные поля в типы
   `Serialize` и строить строку через существующий serde_json.
   Убрать промежуточные карты `Value`. Это участок с наибольшим
   измеренным вкладом, около 1,16 мс на формирование JSON для 128
   узлов. Сложность средняя. Проверить порядок массивов и полей,
   `u64::MAX`, integer/float/boolean, null и представление границ,
   точный размер ответа, лимит Describe и переполнение очереди.
   Цель — сократить часть наблюдаемой стоимости JSON. Сериализация
   всё равно потребуется, фактический выигрыш нужно замерить.
2. **Заменить второй каталог в производном Get живой проверкой
   ключа.** Добавить внутренний `Engine::contains_signal(&str)`.
   Он проверяет физическую карту Engine и точную пару имя
   компонента/имя выхода по формату `signal()`. Идентификаторы
   компонентов и выходов не содержат разделителя `/`.
   `DeviceService::available` использует этот метод под тем же
   mutex Engine, оставляя физическую ветку и `latest` на прежних
   местах. Это устраняет целый измеренный этап, около 199 мкс на
   производный Get при 128 узлах. Сложность низкая. Тестировать
   эквивалентность `catalog().contains_key(key)` для всех ключей,
   некорректных имён, Create/Configure/Delete, потерянных источников,
   пустого кеша и пользовательских реализаций backend. Изменение
   ограничивается `DeviceService` и Engine, интерфейс
   `CommandBackend` сохраняется.
3. **Измерить вариант адресного первого lookup.** Если после п. 2
   нужно убрать и первый полный каталог для Get, добавить
   адресный lookup описания с корректной проверкой ключа,
   унаследованной единицы и `default_poll_period`. Остальные
   операции продолжают использовать общий каталог. При изменении
   API trait реализация по умолчанию должна применять
   `catalog_snapshot` и fallback при `None`. Сложность средняя.
   Пользовательский backend сохраняет собственный `available` и
   может менять результат независимо от каталога.
4. **Рассматривать кеш Describe после прямой сериализации.**
   Кеш принадлежит конкретному сервису или явной версии
   каталога и действий. Инвалидация требуется после успешных
   Create/Delete и Configure со сменой входов, в том числе из-за
   унаследованных единиц всех потомков, а также при замене
   физического каталога или описаний действий. Консервативная
   версия может инвалидировать каждую успешную правку
   конфигурации, включая ParameterSet. Ошибочная правка сохраняет
   прежние данные. При смене формата или лимитов сериализованное
   тело нужно построить заново. ID сериализуется на каждый запрос
   отдельно, лимит проверяется для окончательной строки и framing.
   По текущему формату Describe доступность порта сама по себе не меняет
   описания. Сложность и риск выше из-за нескольких источников
   инвалидации.

Переиспользовать первый снимок для второй проверки было бы безопасно
только при доказанной неизменности графа между двумя чтениями.
Снимок возвращается с освобождённым mutex Engine. Кроме обычных
транспортных путей под `gate`, публичный Session принимает
`CommandBackend`, а прямой вызов методов backend допускает работу
вне `gate`. Поэтому правило «в снимке есть ключ, значит
`available` можно пропустить» нарушает общий контракт. Для
переиспользования снимка потребовался бы связанный с сервисом
маркер версии графа, проверяемый под mutex Engine, и fallback на
живой lookup при расхождении. Адресная проверка сохраняет прежний
момент проверки без такого API.

Данные прежде всего поддерживают локальные изменения Describe и
Get. Разделение `gate` и изменение границы сокетной части TCP
требуют замеров под реальной конкуренцией, включая медленных
подписчиков. Оптимизаций рабочей логики в этом блоке нет.
