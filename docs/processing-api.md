# Общий API компонентов (TCP / WebSocket)

[Краткое руководство пользователя](user-guide.md)

Начальные экземпляры Processing можно задать встроенным списком `[[processing.components]]`
или внешним TOML через `processing.file`. Внешний файл содержит `schema_version = 1` и
список `[[components]]`. Относительный путь разрешается от каталога основного TOML.
Эти способы взаимоисключающие. В обоих случаях экземпляр описывают поля `Configuration`
(`name`, `type_id`, `inputs`, `parameters`, `max_age_ms`) и необязательная таблица
`binding` с `target` и `command_timeout_ms`. [Встроенный пример](../examples/processing.toml)
и [пример с внешним файлом](../examples/virtual-plant-external.toml).
Порядок объявлений свободный. Сервер сортирует полный граф по зависимостям и среди
готовых компонентов выбирает первый по имени. Это определяет и порядок присвоения
`incarnation`. Циклы и неизвестные сигналы прерывают запуск с именем компонента и причиной.
`Create` и `Bind` применяются в памяти до открытия портов и создания сеанса SQLite.
Ревизия начинается с 0 и увеличивается за каждый Create и Bind. Перед изменением
прочитайте её через `list`. `expected_revision` и `state` в TOML не поддерживаются.
EMA начинает в Running, PID — в Shadow. При загрузке привязки выход остаётся в Manual,
команда прибору не отправляется. Auto включается только явно через API.

Операция `components` доступна в протоколе v1. Алгоритмы выбираются по строке `type_id`
из реестра. TCP использует NDJSON, WebSocket передаёт один JSON в текстовом сообщении.
ID — положительные u64, строго возрастающие в пределах соединения. Ошибка операции
также расходует корректный ID. Максимальный размер входного сообщения — 16 КиБ.

```json
{"id":1,"op":"components","command":{"action":"types"}}
```

Успех: `{"id":1,"status":"ok","data":...}`. Ошибка:
`{"id":1,"status":"error","error":"revision_conflict"}`.
Управление компонентами и Save используют общую ревизию. Save отвечает после публикации файла.

| action | Поля command | Результат data |
| --- | --- | --- |
| `types` | нет | Массив TypeDescription: type_id, kind, inputs, outputs, parameters, proposal |
| `list` | offset=0, limit=16 (1…64) | revision, instances, total, next_offset |
| `create` | configuration, expected_revision | Первая страница снимка после изменения |
| `configure` | configuration, expected_revision | Первая страница снимка после изменения |
| `parameter_set` | name, parameter, value, expected_revision (необязательно) | Первая страница снимка после изменения |
| `delete` | name, cascade=false, expected_revision | Первая страница снимка после удаления |
| `bind` | name, target, command_timeout_ms (1…10000), expected_revision | Первая страница снимка; привязка не включает Auto |
| `state` | name, state, expected_revision | Первая страница снимка; допустимы shadow, stopped, auto |
| `outputs` | нет | Массив key, mode, owner, generation, in_flight, outcome_unknown |
| `save` | нет | Объект `{"revision": …}` с ревизией сохранённого снимка |

`save` перезаписывает внешний TOML формата `schema_version = 1` по пути, зафиксированному при загрузке. Для встроенных компонентов возвращается `no_experiment_file`. При изменении ревизии во время подготовки файла возвращается `revision_conflict`, при ошибке записи или замены — `experiment_write_failed`. На одно соединение допускается один ожидающий Save, следующий в той же пачке может получить `runtime_busy`.
Изменения внешнего файла, внесённые другим процессом во время работы сервера, автоматически не обнаруживаются.

В файл записывается полный граф с нормализованными параметрами и актуальными привязками.
Save оставляет режимы контроллеров, владение выходами, состояние алгоритмов и ревизию
в памяти без изменений. При следующем запуске граф строится из TOML, контроллеры
создаются в Shadow, выходы — в Manual. Ревизия и `incarnation` создаются заново.

`list` сортирует экземпляры по имени, ограничивает страницу также 48 KiB данных.
`next_offset=null` означает конец. При нескольких страницах сравнивайте revision;
при изменении конфигурации между страницами перечитайте список. `types` не зависит
от состояния экземпляров. Схема параметра: name, unit, value_type, default.
value_type — tagged object с type=`float`/`integer`/`boolean`/`choice`; у числовых
типов min/max включительны, у choice — values. Float принимает JSON number, integer
требует целое i64; строки и Boolean не преобразуются в числа.

Элемент instances содержит configuration (с заполненными defaults), incarnation,
state, fault (строка причины либо null) и binding. binding=null для непривязанного
контроллера или фильтра; иначе это `{ "target": "furnace1/power", "command_timeout_ms": 1000 }`.
Привязка видна в shadow/auto/stopped/fault, сохраняется при остановке и исчезает при
удалении экземпляра. Повторное создание того же имени не наследует старую привязку.
Все снимки list/create/configure/parameter_set/delete/bind/state имеют одинаковый формат и ревизию;
binding входит в бюджет 48 KiB до выбора next_offset. Возможные состояния в ответах: running
для фильтра, shadow/stopped/fault/auto для контроллера. running и fault нельзя
установить командой оператора. Переход состояния сбрасывает математическую историю;
переход в Auto не обеспечивает bumpless transfer.

В outputs поле owner — null либо пара `[имя_контроллера, incarnation]`, generation —
u64, in_flight — число начатых, ещё не завершённых операций, outcome_unknown — Boolean.
Снимок содержит все выходы приборов с `writable: true`, включая находящиеся в Manual.
Привязка shadow-контроллера сама по себе не создаёт owner. Её можно прочитать из любой
сессии через components/list; повторный bind заменяет target и timeout атомарно по CAS.

В TypeDescription inputs — массив имён входов; outputs — массив `{name,unit}`.
unit=null наследует единицу первого входа в порядке сортировки имён входов.
proposal=null означает отсутствие выхода-кандидата; иначе это имя одного из outputs.
Все имена и схемы передаются клиенту из зарегистрированной фабрики.

## Конфигурация и ревизии

```json
{"name":"smooth","type_id":"ema","inputs":{"input":"furnace1/sample_temperature"},"parameters":{"tau":2.0},"max_age_ms":5000}
```

name/type_id — 1…64 ASCII букв, цифр, `_`, `-`, `.`. Имя экземпляра уникально.
inputs — точное соответствие именам входов фабрики. Входы числовые,
источники должны быть периодически опрашиваемыми сигналами либо выходами компонентов.
`max_age_ms` обязателен, 1…86400000; независимый watchdog проверяет возраст при отсутствии
новых событий. В RAM допускается до 128 экземпляров, у типа до 8 входов/выходов и 32 параметров.
Дополнительно проверяется бюджет каталога для `describe`: при превышении возвращается
catalog_capacity до изменения графа. Поэтому допустимое число экземпляров зависит от числа
выходов, длины имён и физического каталога. Каталог не становится недоступным из-за размера
новых производных сигналов.

`parameters` можно опустить: применяются defaults. `configure` заменяет **всю** конфигурацию;
пропущенные параметры возвращаются к defaults, это не patch. Тип существующего экземпляра
не меняется. Неизвестные поля и параметры отклоняются. При rewire сбрасываются зависимые
состояния; зависимые контроллеры переходят в fault. Настройка самого Auto-контроллера требует
сначала остановить его. Изменение tau сохраняет состояние EMA и время последнего образца.

`parameter_set` изменяет один параметр актуальной серверной конфигурации за один запрос:

```json
{"id":10,"op":"components","command":{"action":"parameter_set","name":"loop","parameter":"setpoint","value":35.0}}
```

Чтение конфигурации клиентом не требуется. Без expected_revision (или с null) сервер
под общей блокировкой берёт актуальную конфигурацию, заменяет параметр и выполняет
обычный configure/reconfigure. С expected_revision проверяется CAS; несовпадение даёт
revision_conflict. Другие параметры, inputs, type_id, max_age_ms и binding сохраняются.
Успех увеличивает общую revision ровно на один, в том числе при повторной записи того же
значения; ошибка не меняет конфигурацию, состояние или ревизию. Параллельные изменения
разных параметров без CAS сохраняются оба. Неизвестный параметр, неверный тип/диапазон
или сочетание значений (например output_min >= output_max) отклоняются общей валидацией.
Integer передаётся целым JSON i64, Float — конечным числом, Boolean — true/false,
Choice — строкой из values. В Auto перенастройка PID запрещена (stop_before_configure).
Изменение параметра сохраняет подписки и не включает Auto, не отправляет физический set.

Изменение inputs завершает через observation_stream_closed все существующие подписки,
содержащие выход изменённого компонента или его потомков, даже если новый вход находится
на том же физическом порту. Уже опубликованный старый префикс может быть доставлен перед
терминальным событием; значения нового графа в него не добавляются. Закрытие необратимо
в текущей сессии: нужна новая сессия и подписка. Независимые подписки и настройка одних
параметров не закрываются. Переподключение графа не создаёт observation_data_lost.

revision — общая конфигурационная ревизия сервера, изначально 0. Каждый успешный create,
configure, parameter_set, delete, bind или state увеличивает её на один. Ошибка проверки ничего не меняет.
Ошибки runtime и новые измерения не увеличивают revision. incarnation уникален для каждого
создания; повторное создание имени получает новый incarnation. Счётчики не оборачиваются.

Выходы называются `processing/<name>/<output>`. Они появляются в обычном describe,
доступны через get/subscribe и readonly. Поля каталога описаны в [протоколе v1](protocol.md#каталог-и-значения).
`poll_period_ns=1000000` у производного сигнала обозначает доступность кеша/подписки
для v1-клиентов, **не обещает частоту вычисления 1 kHz**. Вычисления идут по входным событиям.
Первый get до измерения возвращает no_data. Ошибка вычисления/входа возвращается обычным
measurement со status=error. Удаление завершает затронутые подписки через
observation_stream_closed; повторное создание имени не восстанавливает старую подписку.

## EMA и PID как зарегистрированные типы

EMA: type_id=`ema`, вход `input`, выход `value`, tau=1 s по умолчанию, диапазон
0.000001…86400 s. Первое значение равно входу; alpha=-expm1(-dt/tau).

PID: type_id=`pid`, вход `input`, выходы error/p/i/d/unconstrained/output/setpoint.
`processing/<name>/setpoint` — readonly Float с единицей входа (например degC),
публикуется в Shadow и Auto вместе с остальными результатами на каждом входном образце,
с тем же временем измерения и метаданными. После изменения уставки новое значение
появится на следующем успешном вычислении; get до него возвращает последний образец.
Используются обычные describe/get/subscribe по TCP и WS. kp/ki/kd остаются параметрами.
defaults: setpoint=0, kp=1, ki=kd=0, output_min=0, output_max=100, max_gap=10 s.
setpoint и границы выхода: ±1e12; коэффициенты: 0…1e12;
max_gap: 0.000001…86400 s; обязательно output_min < output_max.
Производная берётся по измерению, интегратор использует conditional anti-windup.
Первый образец не добавляет I/D. Обратное/повторное время, большой разрыв, потеря,
устаревший вход или нечисловой результат переводят контроллер в fault.

Созданный PID работает в shadow и не пишет прибору. После потери фильтры могут начать
с первого достоверного образца нового поколения. Контроллер остаётся fault до явного
`state=shadow`; переход в Auto разрешается отдельно, после готовности свежего входа.

## Управление выходами

Пример динамического переключения фильтра (для каждой мутации с CAS используйте
актуальную revision из ответа предыдущей операции):

1. Создать EMA smooth и PID loop с входом processing/smooth/value; выполнить bind,
   дождаться свежего входа и явно включить state=auto.
2. Вернуть loop в state=shadow: право управления освобождается, мощность не обнуляется.
3. Создать EMA smooth2 и через configure заменить input PID на processing/smooth2/value,
   сохранив остальные поля полной конфигурации.
4. PID получает fault=input_changed, его история сбрасывается; затронутая подписка
   завершается observation_stream_closed. Нужны новая сессия/подписка, явный state=shadow
   и свежий образец. Автоматического восстановления Auto нет.
5. Через configure вернуть input на processing/smooth/value. Снова восстановить Shadow
   и подписку. Удалить smooth2 без cascade; PID остаётся в графе. После свежего образца
   можно явно включить Auto. Пока PID зависит от smooth2, delete без cascade запрещён.

Отдельной команды сброса интегратора нет. Переходы состояния, изменение
входов и инвалидирование состояния сбрасывают историю PID; перенастройка параметров
сохраняет её, ограничивая интегратор новыми границами выхода.

```json
{"id":2,"op":"components","command":{"action":"bind","name":"loop","target":"furnace1/power","command_timeout_ms":1000,"expected_revision":2}}
```

Bind требует shadow и writable numeric target. Auto требует shadow, привязку и свежие
достоверные входы; один выход принадлежит одному incarnation контроллера. Manual — отсутствие
Auto-владельца. Для перехода в Manual отправьте state=stopped или shadow владельцу.
Ручной set в Auto возвращает output_owned. Generic actions консервативно проверяют
все writable-выходы своего прибора; имена действий и алгоритмов не анализируются.

Контроллер имеет не более одной ожидающей команды. Новые вычисления во время ожидания
публикуют диагностику, не ставят повторную запись. Deadline ограничен timeout и свежестью
всех непосредственных входов. В PortWorker проверяются поколение владельца, поколения
исходных портов, их остановка и deadline. Отзыв разрешения отменяет ещё не начатые команды.
Начатую запись отменить нельзя; новый Auto-владелец не получает выход до её завершения.

При неопределённом результате выставляется `outcome_unknown`. Позднее завершение
не порождает второго ответа и не снимает блокировку Auto. Автоматических повторов нет.
Явный ручной set/action оператора выполняется как отдельный запрос в очереди порта. Чтобы вновь разрешить Auto
после outcome_unknown, требуется перезапуск сервера. Фактическое состояние прибора
проверяет оператор.

При остановке/удалении/каскадном удалении/потере/устаревании/ошибке/shutdown разрешение
отзывается. Это освобождение права записи, а не подтверждение нулевой мощности на приборе.
Автоматическая «безопасная запись» не отправляется. Физические interlock/watchdog и проверка
безопасного состояния установки остаются вне этой реализации.

Float proposal проверяется до преобразования. Integer target округляется к ближайшему
целому, половины от нуля, с проверками диапазона до и после. Например, для Arduino power
2.5 → Integer(3), -0.1 и 100.1 отклоняются, а не обрезаются. Boolean targets запрещены.

Основные ошибки: revision_conflict, revision_exhausted, unknown_type, invalid_instance,
unknown_instance, unknown_parameter, invalid_parameter:<name>, invalid_inputs,
unknown_or_non_numeric_input, dependency_cycle, signal_collision, has_dependents,
stop_before_configure, invalid_state, not_controller, restart_in_shadow_first,
input_not_ready, output_not_bound, invalid_timeout, invalid_output_target,
stop_in_shadow_before_bind, output_owned, output_busy, output_fault, invalid_output,
invalid_page, catalog_capacity, instance_too_large. Последняя ошибка означает, что один
экземпляр с метаданными не помещается в страницу; пустая страница с тем же next_offset
не возвращается. Ошибки структуры имеют префикс invalid_component_request:.

## SQLite и время

У серверных портов режим Managed: физические set/action требуют Permit общей Authority
непосредственно в worker. Прямой низкоуровневый Rust-вызов без него возвращает
output_not_authorized и не передаёт байтов драйверу. Правила композиции и совместимость
Rust API описаны в [managed-ports.md](managed-ports.md).

Recorder использует SQLite со схемой `user_version = 3` и `application_id = 0x4c414252`.
Собственные базы v1 и v2 транзакционно мигрируют по цепочке v1 → v2 → v3 или v2 → v3.
Чужие базы и неподдерживаемые версии отклоняются. [Схема и миграции SQLite](audit.md#sqlite-и-миграция).

В `measurements.source_metadata` хранятся десятичные строки `source_instance`, `sequence`,
`generation` (u64) и `elapsed_ns` (u128). `Instant` используется только в памяти.
`record_order` хранит общий порядок принятых строк `measurements` и `events` через
`kind` и `row_id`. Исходное событие записывается перед его производными. Строки из v1
остаются без метаданных и общего порядка. Аудит хранится отдельно в `audit_events`.

Метаданные источника отсутствуют в пакетах `measurement` протокола TCP/WS v1. При потере
непрерывности подписка завершается явной ошибкой. Конфигурацию Processing сохраняет
`save` во внешнем TOML, который сервер читает при запуске. Ревизия, владение выходами,
значения сигналов, история EMA и интеграл PID между запусками не восстанавливаются.
