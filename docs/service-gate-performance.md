# Конкуренция за DeviceService::gate

Первый замер для базы `b1aa3148c04ee9aa3767d5eca9e1bbaeff5a5044`.
Границы критических секций и рабочие алгоритмы сохранены. Измеритель
компилируется с Cargo feature `gate-metrics`.

## Точки захвата

| Категория | Вызов | Что входит в удержание |
| --- | --- | --- |
| `manage` | `DeviceService::manage` | Синхронное управление, включая проверку графа, согласование выходов, каталог, lineage, кеш и страницу результата при изменениях. |
| `apply_event` | `DeviceService::apply_event_recorded` | Исходное событие, Continuity, Engine, согласование контроллеров, кеш, fanout и callback записи. |
| `tick` | `DeviceService::tick_recorded` | Проверка свежести, согласование команд и возможная инвалидация. |
| `receive_message` | `DeviceService::receive_message` | Разбор и диспетчеризация текста Session, включая каталог по запросу. WebSocket читает и отправляет кадры за пределами этой секции. |
| `stop_controls` | `DeviceService::stop_controls` | Закрытие допуска и освобождение владения. |
| `tcp_drive` | `DeviceService::drive_connection` | Целый оборот, включая неблокирующие чтение и запись сокета, диспетчеризацию, выдачу завершённых запросов и наблюдений. Включены пустые обороты. |

`components` внутри уже захватившего gate транспорта относится к
соответствующей транспортной категории. Подсчёт ведётся по фактическим
захватам mutex. Физические команды завершаются асинхронно, и ожидание
драйвера не добавляется к времени ожидания gate.

## Что измеряется

`wait` начинается перед `Mutex::lock` и заканчивается сразу после захвата.
`hold` начинается в той же точке и заканчивается по метке непосредственно
перед освобождением. RAII освобождает mutex перед обновлением атомарных
счётчиков и выдерживает ранний возврат. Метки включают стоимость чтения
часов и планирование ОС. Возможна задержка между последней меткой и
фактическим unlock. Измерения атомиков после unlock не входят в hold, но
могут влиять на планирование нагрузки.

На категорию хранятся счётчик, суммы, максимумы и две гистограммы.
Каждый диапазон между степенями двойки делится на восемь корзин, отдельно
учитывается ноль. Верхняя граница корзины округляет процентиль вверх максимум
на 12,5% от нижней границы для длинных интервалов. Для самых коротких
значений корзины имеют шаг 1 нс, хотя фактическое разрешение часов
может быть хуже. Максимумы и суммы получаются из измеренных значений.
В CSV и таблицах времена в микросекундах.

Снимок не захватывает mutex сервиса. Benchmark снимает его после
завершения участников, поскольку параллельный снимок может увидеть часть
атомарных обновлений. Сброс требует исключительного владения сервисом.
При отключённой feature сохраняется обычный `MutexGuard` без часов и
статистики.

## Воспроизведение

```powershell
$env:CARGO_TARGET_DIR = 'D:\rust_projects\lab-server-agent-build'
cargo run --release --locked --features gate-metrics --example service_gate_bench > gate-run.csv
```

Windows 10 Pro 22H2 (19045), AMD Ryzen 5 6600H (6 ядер, 12 логических),
rustc 1.95.0 (`x86_64-pc-windows-msvc`), стандартный Cargo Release.
На каждый повтор создаётся новый сервис с одним физическим числовым
сигналом. Имитационный порт создаёт собственную идентичность источника.
Поток PortWorker не запускается. Измерения подаются на штатную границу
агрегатора через `apply_event_recorded` с действительными поколением,
идентичностью, строго возрастающими sequence и монотонными метками.

- Один образец заполняет кеш, затем выполняются восемь раундов прогрева
  выбранной нагрузки. После завершения участников статистика сбрасывается.
- В каждом измеряемом раунде участники стартуют через общий Barrier.
  Прямые сценарии выполняют 256 раундов, loopback — 64. На раунд приходится
  одно исходное измерение. Прямой клиент посылает один запрос на раунд.
  TCP и WebSocket чередуют `ping`, `get` последнего производного сигнала
  и `describe`, со сдвигом на один запрос между ними. В каждом соединении
  одновременно ожидается максимум один ответ.
- После раундов проверяется актуальное конечное значение. При rewire
  отдельный пробный образец проверяет последнюю конфигурацию за пределами
  замера. Счётчики числа событий, ревизии, соответствие ID и содержимое
  ответов проверяются. В подписанном варианте каждый клиент дополнительно
  читает ровно одно производное измерение раунда и проверяет его метку.
- В loopback используются настоящие серверные адаптеры и локальные сокеты
  с TCP_NODELAY. Измеряемые соединения открываются заново после прогрева.
  В статистику входят установка подписок, пустые циклы TCP и завершение
  соединений. TCP/WS работают параллельно. Время ответа клиента не замерялось.
- После основной серии отдельно выполняется один `stop_controls` на
  повтор. В этих замерах выходов в Auto и ожидающих записей нет.

| Сценарий | Нагрузка | Потоки |
| --- | --- | ---: |
| `baseline` | Только измерения | 1 |
| `requests` | Измерения и по одному Session для каждого вида запроса | 4 |
| `retune` | Измерения, чередование Configure и ParameterSet для tau при прежних связях | 2 |
| `rewire` | Измерения и Configure, меняющий вход второго узла между физическим сигналом и первым EMA. Обе ветви обновляются на исходном образце. | 2 |
| `watchdog` | `requests` плюс tick каждые восемь раундов | 5 |
| `loopback` | Измерения, один TCP и один WebSocket, без подписок | 5 |
| `loopback_subscribed` | Тот же loopback с подпиской каждого клиента на один последний сигнал | 5 |
| `tree_requests` | `requests`, граф из 128 EMA в форме двоичного дерева | 4 |
| `shadow_pid` | `watchdog`, последний из 128 узлов заменён PID в Shadow без привязки | 5 |

Основные сценарии выполнены для 1, 8, 32 и 128 узлов. Rewire второго узла
доступен с 8 узлов. По пять повторов на комбинацию. SQLite, физическое
оборудование, реальные частоты портов, медленные клиенты и искусственная
перегрузка отсутствуют. Пропускная способность сервера и задержка на
оборудовании требуют отдельных сценариев.

### Интерпретация

- **Длиннейшее удержание.** При 128 узлах rewire дал hold p99 9437 мкс
  и максимум 16091 мкс. В этом режиме manage занял суммарно около 2020 мс
  на 256 операций в медианном повторе, а измерения — около 116 мс
  удержания. Измерения ждали gate с p99 8686 мкс.
- **Наибольшая занятость без правок графа.** В `requests` при 128 узлах
  смешанные вызовы Session заняли около 652 мс на 768 захватов, измерения —
  105 мс на 256. Суммарное ожидание трёх клиентов может включать одинаковые
  интервалы времени, поэтому его нельзя считать временем занятости mutex.
  В `watchdog` сам tick удерживал gate с p99 42 мкс и ждал с p99 2714 мкс.
- **Сравнение хвостов.** При 128 узлах p99 одного оборота TCP составляет
  около 2216–2359 мкс по двум вариантам loopback. В `requests` p99
  удержания Session составляет 2359 мкс, p99 ожидания измерения —
  2884 мкс. Это показывает, что длинные секции появляются и без сокетов.
  Изолированная обработка измерений занимает 346 мкс по p99. Rewire даёт
  самый длинный хвост среди протестированных режимов. Данных для
  разложения TCP-оборота на сокет, конкретные запросы и fanout пока нет.
- **Масштабирование.** От 1 до 128 узлов p99 удержания измерения в
  `baseline` вырос примерно в 22 раза, p99 удержания Session в
  `requests` — в 24 раза. У rewire рост особенно заметен между 32 и
  128 узлами. Дерево из 128 EMA в `tree_requests` даёт hold p99
  измерения 786 мкс против 721 мкс у цепочки, а hold p99 запросов
  совпадает на уровне корзины 2359 мкс. Одного графа каждой формы
  недостаточно для обобщения этого сравнения.
- **Lineage и dependents.** В отдельном микробенчмарке ядра на 128 узлах
  `lineage` для цепочки занимал 97 мкс, один вызов `dependents` —
  2892 мкс. В сервисном замере медиана p50 удержания управлением выросла
  с 1180 мкс для retune до 8389 мкс для rewire. Rewire повторяет обход
  зависимых для списка сбрасываемых выходов и инвалидации, а также
  сбрасывает историю и затрагивает подписки. Разницу нельзя целиком
  отнести к `dependents`. Оба варианта пересчитывают `lineage`, поэтому
  этот эксперимент не изолирует его вклад. Сценарий PID в Shadow
  проверяет путь вычисления, а lineage при подаче предложения Auto
  требует отдельного замера. [Микробенчмарк ядра](processing-architecture.md#измерения-в-release).
- **Подписчики.** При 128 узлах подписанный режим увеличил медианное
  число TCP-захватов с 75 до 134 на те же 64 запроса. Суммарное
  удержание изменилось примерно с 42,80 до 43,62 мс. Удержание измерения
  по p50 выросло с 393 до 459 мкс. Большая доля коротких оборотов в
  подписанном режиме снижает p50 TCP. Этот сценарий ограничен двумя
  быстро читающими клиентами и одним ключом на каждого.

## Что проверять следующим

1. **Повторный обход при rewire.** Измерить оба прохода `dependents` и
   инвалидацию по отдельности, затем проверить возможность передавать уже
   вычисленный набор зависимых между этими этапами. Здесь зафиксирован
   самый длинный hold, а равенство порядка инвалидации и аудита можно
   проверить действующими регрессиями.
2. **Путь каталога у запросов.** Разделить счётчики `ping`, `get` и
   `describe`. Измерить построение каталога, повторную проверку
   доступности производного сигнала и сериализацию `describe`. Эти
   пути создают большую суммарную занятость в сценарии без изменения графа.
3. **Происхождение сигналов.** Измерить `physical_lineage` и
   `Engine::lineage` внутри Configure и Auto с имитационным исполнителем.
   Отдельно проверить несколько физических портов и несколько Auto
   предложений за пакет, где расчёт повторяется.
4. **Границы TCP и mutex.** Разметить пустые обороты, чтение,
   диспетчеризацию и запись TCP. Добавить больше подписчиков и сценарий
   с медленным клиентом. Пока самые длинные измеренные секции связаны
   с rewire, а высокий p99 есть и у Session без сокета. Текущих данных
   достаточно для приоритизации локальных измерений. Решение о границах
   I/O или архитектуре блокировок требует дополнительных данных.

Раунды выравнивают попытки захвата и тем самым формируют искусственное
соперничество. Сценарии запускались на одной машине в фиксированном
порядке. Планировщик, разрешение часов и инструментирование влияют
на хвосты, особенно при малом числе наблюдений. Для 64 TCP/WS-запросов
p99 может совпадать с максимумом. Измеренные интервалы не являются
гарантией хвостовой задержки в рабочем сервере.
