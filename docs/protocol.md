# Протокол lab-server v1

[Краткий справочник и запуск](../README.md) · [Архитектура](architecture.md)

## Формат обмена

TCP, NDJSON, UTF-8: одно JSON-сообщение на строку, завершённую LF (`\n`).
Сообщение — JSON-объект; имена полей не должны повторяться. Максимальный размер входного кадра — **16 KiB без LF**.
Границы чтений из TCP не совпадают с границами сообщений: клиент должен собирать строки до LF.

- Каждый запрос содержит `id` и строковое поле `op`.
- `id` — положительное целое `u64` (1…18446744073709551615), строго возрастающее в пределах соединения.
  Даже отклонённая команда расходует корректный новый ID; некорректный JSON, повторные поля и неверный ID — нет.
  Перед исчерпанием диапазона нужно открыть новое соединение.
- Повторный или меньший ID вызывает `duplicate_id` **без поля `id`**; исходный pending-запрос сохраняется.
- Ответы сопоставляются с запросами по `id`. Асинхронные события `measurement` не имеют `id`.
  Ответы и события могут чередоваться; порядок ответов не обязан совпадать с порядком запросов.

## Команды

Обязательные для всех команд поля — `id` и `op`; дополнительные поля указаны в таблице.
JSON-примеры запросов нужно отправлять с завершающим LF. Примеры ответов предполагают указанные ID.

| `op` и назначение | Дополнительные обязательные поля | Пример запроса | Успешный ответ |
| --- | --- | --- | --- |
| `hello` — версия протокола | — | `{"id":1,"op":"hello"}` | `{"id":1,"status":"ok","protocol":"lab-server","version":1}` |
| `describe` — каталог параметров и действий | — | `{"id":2,"op":"describe"}` | `id`, `status: "ok"`, массивы `parameters` и `actions` |
| `ping` — проверка связи | — | `{"id":3,"op":"ping"}` | `{"id":3,"status":"ok"}` |
| `get` — получить значение | `key`: строка | `{"id":4,"op":"get","key":"furnace1/heater_temperature"}` | `id`, `status: "ok"`, `key`, `value`, `unit`, `completed_at_unix_ms` |
| `set` — записать значение | `key`: строка, `value`: число или Boolean | `{"id":5,"op":"set","key":"furnace1/power","value":20}` | `{"id":5,"status":"ok"}` |
| `subscribe` — добавить подписки | `keys`: массив строк; либо одиночный `key` | `{"id":6,"op":"subscribe","keys":["furnace1/heater_temperature"]}` | `{"id":6,"status":"ok","keys":["furnace1/heater_temperature"]}` при отсутствии других подписок |
| `unsubscribe` — удалить подписки | `keys`: массив строк | `{"id":7,"op":"unsubscribe","keys":["furnace1/heater_temperature"]}` | `{"id":7,"status":"ok","keys":[]}` при удалении последней подписки |
| `invoke_action` — выполнить действие без аргументов | `key`: глобальное имя действия | `{"id":17,"op":"invoke_action","key":"furnace1/apply"}` | `{"id":17,"status":"ok"}` |

### Действия устройств

`describe.actions` — отдельный массив объектов с `key` и человекочитаемым `description`.
Например, драйвер, поддерживающий действие `apply`, может объявить элемент:

```json
{"key":"furnace1/apply","description":"Применить настройки"}
```

Имена определяет драйвер; ядро не придаёт `apply` или `reset` специального значения.
`parameters` сохраняет прежний формат, `hello.version` остаётся 1. Без действий возвращается
`actions: []`. Драйвер Arduino предоставляет `apply` и `reset` (см. ниже).

Драйвер реализует `actions() -> Vec<ActionDescription>` (`name`, `description`) и
`invoke_action(action, io) -> Result<(), DriverError>`. По умолчанию каталог действий пуст.
`DeviceRegistry` регистрирует глобальные имена; `CommandRouter::invoke_action(id, key, deadline)`
передаёт локальное имя соответствующему `PortWorker`. Действия, чтения, записи и опрос
последовательно используют один `DeviceIo` физического порта. Аргументов и отдельного журнала
действий нет; действия сами по себе не создают наблюдений или записей SQLite.

TCP и WebSocket выполняют команду через общие `Session` и `DeviceService` с прежними лимитами
очереди и pending. Неизвестное устройство или действие даёт `status: "error", error: "unknown_key"`.
Дедлайн — 10 с с учётом очереди; гарантии `runtime_timeout` и `outcome_unknown` совпадают с `set`
(см. ниже). Ошибка драйвера после начала означает `outcome_unknown` даже при синхронизированном
порте; десинхронизация или отключение останавливает этот порт. Повторов нет. Потеря соединения
или прекращение ожидания клиентом не отменяет принятую команду и не доказывает её неисполнение.
ID защищает от повторной обработки только внутри соединения; новый ID или новое соединение
означает новый запрос, поэтому автоматически повторять действие после неизвестного исхода нельзя.

### Arduino Designer

Драйвер рассчитан на [thermal-plant-uno, ревизия 337e6a7](https://github.com/alexandervolkov1/thermal-plant-uno/tree/337e6a7bc0d7c65eeca7e0f81c217a20e4e50caf).
Помимо прежних четырёх Operator-параметров он предоставляет 19 параметров с префиксом `designer/`:

```text
heater.capacity    sample.capacity    room.capacity
coupling           heater.loss        sample.loss
room.loss          heater.radiation   sample.radiation
heater.max_power   initial.heater     initial.sample
initial.room       background.temp    seed
parameter.spread   power.fluctuation  sensor.noise
sensor.drift
```

Все доступны для `get/set`, без периодического опроса по умолчанию. `seed` — `integer`
от 0 до 4294967295; остальные, включая `room.capacity`, — `float` в диапазоне
от `-f32::MAX` до `f32::MAX` (приблизительно ±3.4028234663852886e38), без дополнительных
физических ограничений в каталоге. Для JSON float нужны точка или экспонента: `350000.0`,
а не `350000`; для `seed` наоборот нужен целочисленный литерал. Значения JSON проходят
существующий разбор в `f64`, затем округляются до `f32` к ближайшему с выбором чётного при равенстве.
Исходный десятичный текст драйверу недоступен: в редких случаях двойное округление отличается
от прямого decimal → `f32`; например, `1e-400` уже становится нулём в общем JSON-парсере.
Это ограничение протокола v1 сохранено, проверка ниже относится к полученному `f64`.
Драйвер отвергает нечисла, бесконечности и ненулевые `f64`, округляющиеся до нуля.
Он передаёт короткую экспоненциальную запись, сохраняющую биты `f32`, включая `-0.0`.
Так обходится особая целочисленная грамматика `room.capacity` в прошивке; `get` возвращает
значение `f32`, точно расширенное до `f64`, поэтому видимое десятичное число может отличаться от заданного.

Пример для режима `--config`, одинаковый для TCP и WebSocket. Отправляйте следующий запрос
после ответа на предыдущий; в TCP добавляйте LF, в WS используйте отдельный Text message:

```json
{"id":1,"op":"set","key":"furnace1/designer/room.capacity","value":350000.0}
{"id":2,"op":"set","key":"furnace1/designer/seed","value":12345}
{"id":3,"op":"get","key":"furnace1/designer/room.capacity"}
{"id":4,"op":"invoke_action","key":"furnace1/apply"}
{"id":5,"op":"invoke_action","key":"furnace1/reset"}
```

Designer `get` читает **staged**-конфигурацию, а `set` изменяет только её. `apply` проверяет
полную staged-конфигурацию и при успехе делает её активной. `reset` отбрасывает staged-правки
и восстанавливает активную конфигурацию. Оба успешных действия перезапускают моделирование
и устанавливают мощность 0% в самой прошивке; драйвер не посылает дополнительный `set power`.
Кеш Operator обновляется очередным опросом, поэтому сразу после действия `get power` может
ещё вернуть прежнее значение. Запись SQLite и правила опроса Operator сохраняются.

Ограничение протокола v1: даже явный ответ `@id err config` после начала `apply/reset` клиент получает
как `outcome_unknown`; исходный `DriverError` при этом синхронизирован, порт продолжает работать.
Та же консервативная семантика `set` распространяется на проверку потери ненулевого значения
при преобразовании в `f32`, выполненную драйвером до отправки команды. Повторов нет.
Повреждённые, неполные или некоррелированные ответы останавливают только соответствующий порт.
Действия доступны через общий слой TCP и WebSocket.

### Каталог и значения

В `describe.parameters` каждый объект содержит `key`, `type`, `min`, `max`, `unit`, `writable`, `poll_period_ns`.
`type` принимает `integer`, `float` или `boolean`. Для числовых типов границы `min` и `max` включительны.
Для `boolean`: `min: null`, `max: null`, `unit: ""`; оба значения `true` и `false` допустимы без числовых ограничений.
`poll_period_ns` — период опроса в наносекундах, либо `null`, если периодического опроса нет.
Например, элемент каталога для `power` (это фрагмент ответа `describe`):

```json
{"key":"furnace1/power","type":"integer","min":0,"max":100,"unit":"%","writable":true,"poll_period_ns":1000000000}
```

Пример булевых параметров имитационного драйвера (они не входят в каталог Arduino):

```json
{"key":"switch/enabled","type":"boolean","min":null,"max":null,"unit":"","writable":true,"poll_period_ns":null}
{"key":"switch/fault","type":"boolean","min":null,"max":null,"unit":"","writable":false,"poll_period_ns":10000000}
```

Operator-каталог Arduino; у этих четырёх параметров период опроса — 1 с (`1000000000` нс):

| `key` | `type` | Диапазон | `unit` | `writable` |
| --- | --- | --- | --- | --- |
| `furnace1/sample_temperature` | `float` | −250…1500 | `degC` | `false` |
| `furnace1/heater_temperature` | `float` | −250…1500 | `degC` | `false` |
| `furnace1/room_temperature` | `float` | −250…1500 | `degC` | `false` |
| `furnace1/power` | `integer` | 0…100 | `%` | `true` |

Для `set` литералы `20` и `20.0` различаются: первый — `integer`, второй — `float`.
Запись требует `writable: true` и соответствия типу и диапазону; `20.0` для `power` будет отклонено.
Экспоненциальная запись также считается `float`; бесконечные значения и целые за пределами `i64` не принимаются.
Boolean передаётся JSON-литералами `true` и `false`, без кавычек. Неявных преобразований между Boolean и числами нет:
для булевого параметра `1`, `0`, `1.0`, `0.0` и строка `"true"` отклоняются до обращения к драйверу;
для числового параметра `true` и `false` также недопустимы. Например, запросы к имитационному драйверу:

```json
{"id":8,"op":"set","key":"switch/enabled","value":true}
{"id":9,"op":"set","key":"switch/enabled","value":false}
```

Успешный ответ `set` остаётся ACK с `id` и `status: "ok"`. Правила таймаута и `outcome_unknown` одинаковы для всех типов.

`get` периодически опрашиваемого параметра возвращает последнее измерение, включая последнюю ошибку чтения.
Если измерений ещё нет, ответ имеет `status: "no_data"`. Для параметра без периодического опроса выполняется отдельное чтение.
Варианты ответа на `get` (альтернативы, не несколько ответов на один запрос):

```json
{"id":4,"status":"ok","key":"furnace1/heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"id":4,"status":"no_data","key":"furnace1/heater_temperature"}
{"id":4,"status":"error","key":"furnace1/heater_temperature","error":"Empty response","completed_at_unix_ms":1700000000000}
```

Успешный `get` булевого параметра возвращает JSON Boolean, а не число или строку; `unit` всегда пустая строка.
Например, после записи `enabled` в имитационном драйвере:

```json
{"id":10,"op":"get","key":"switch/enabled"}
{"id":10,"status":"ok","key":"switch/enabled","value":false,"unit":"","completed_at_unix_ms":1700000000000}
```

### Подписки

Подписки индивидуальны для каждого TCP/WS-соединения. Подписаться можно только на периодически опрашиваемые параметры.
Повторное `subscribe` идемпотентно: оно добавляет ключи к текущему набору, а не заменяет его.
`subscribe` также принимает `{"id":8,"op":"subscribe","key":"furnace1/heater_temperature"}`; одновременно `key` и `keys` передавать нельзя.
`unsubscribe` принимает только `keys`, без одиночного `key`. Пустой `keys: []` ничего не изменяет, в том числе не удаляет все подписки.
Дубликаты ключей удаляются. Успешный ответ обеих команд содержит актуальный полный список `keys`, отсортированный по имени.
Изменение набора атомарно: неизвестный или неподписываемый ключ приводит к отказу всего запроса.

## Асинхронные события

Примеры успешного измерения и ошибки чтения:

```json
{"event":"measurement","status":"ok","key":"furnace1/heater_temperature","value":25.0,"unit":"degC","completed_at_unix_ms":1700000000000}
{"event":"measurement","status":"error","key":"furnace1/heater_temperature","error":"Empty response","completed_at_unix_ms":1700000001000}
```

Для булевого параметра `value` — JSON Boolean, `unit` — пустая строка. Примеры событий `fault` имитационного драйвера:

```json
{"event":"measurement","status":"ok","key":"switch/fault","value":true,"unit":"","completed_at_unix_ms":1700000000000}
{"event":"measurement","status":"ok","key":"switch/fault","value":false,"unit":"","completed_at_unix_ms":1700000000010}
{"event":"measurement","status":"error","key":"switch/fault","error":"simulated read failure","completed_at_unix_ms":1700000000020}
```

Добавление Boolean не меняет версию протокола: `hello.version` остаётся `1`.

`completed_at_unix_ms` — время завершения измерения в миллисекундах от Unix epoch, а не время отправки клиенту.
При ошибке чтения вместо `value` и `unit` передаётся строка `error`; поля `id` у событий нет в обоих случаях.
ACK (`status: "ok"`) для `subscribe` предшествует событиям новых подписок; публикации до их активации не воспроизводятся.
События следуют порядку публикации. После ACK `unsubscribe` новые измерения удалённого ключа не приходят;
уже поставленные в отправку события могут предшествовать ACK. Переподключение не восстанавливает пропущенные наблюдения.

## Ошибки и ограничения

Ошибка запроса обычно имеет поля `id`, `status: "error"`, `error`; для ошибки конкретного ключа может присутствовать `key`.
Если ID нельзя однозначно извлечь, он отсутствует. `duplicate_id`, ошибки кадра и завершения потока приходят без `id`.
Например: `{"status":"error","error":"duplicate_id"}` или `{"status":"error","error":"observation_data_lost"}`.

| Группа | Значения `error` и смысл |
| --- | --- |
| Кадр | `empty_frame`, `frame_too_long`, `invalid_utf8`, `incomplete_frame` (EOF до LF); соединение завершается |
| JSON | `invalid_json`, `expected_object`, `duplicate_key` |
| Поля запроса | `invalid_id`, `unsupported_op`, `invalid_key`, `invalid_value`, `invalid_keys` — неверное или отсутствующее поле |
| Уникальность ID | `duplicate_id` — повторный или меньший ID |
| Параметр и запись | `unknown_key`; `Parameter is read-only`; `Value does not match parameter spec` |
| Подписки | `not_subscribable` — нет периодического опроса; `too_many_subscriptions` — превышен лимит |
| Очереди | `too_many_pending` — лимит ожидающих запросов клиента; `runtime_busy` — очередь команд заполнена; `runtime_unavailable` — порт недоступен или остановлен |
| Ожидание | `runtime_timeout`, `outcome_unknown` — различия для `set` и `invoke_action` описаны ниже |
| Поток наблюдений | `observation_data_lost` — потеря данных; `observation_stream_closed` — закрытие без обнаруженного переполнения |

Ошибки чтения содержат текст драйвера или ввода-вывода, например `Empty response`; это не закрытый перечень кодов.
Ожидание `set`, `invoke_action` и отдельного чтения `get` ограничено 10 с, включая очередь.
Для `set` и `invoke_action` используется общий механизм `SetExecution`:

- `runtime_timeout`: исполнение не началось; просроченная команда не будет отправлена устройству.
- `outcome_unknown`: исполнение началось, но результат неизвестен из-за таймаута, потери ответа или ошибки драйвера. **Автоматически повторять операцию нельзя.**
- Уже доступный результат имеет приоритет над таймаутом; поздний результат не порождает второго ответа.

При переполнении очереди порта подписанный на него клиент, а при персональном переполнении владелец очереди получает `observation_data_lost`, и повреждённый поток завершается.
После этого нужно новое соединение и новая подписка. Потеря при активной подписке не сбрасывается через `unsubscribe` → `subscribe` до уведомления.
Потеря в период без подписок не мешает последующей подписке (кроме насыщения u64::MAX); клиенты без подписок сохраняют соединение и pending-команды.
Переполнение выходного буфера или транспортная ошибка могут привести к закрытию без сообщения об ошибке.
EOF не доказывает полноту доставки измерений или неисполнение ожидающего `set` / `invoke_action`.

| Ресурс | Лимит |
| --- | --- |
| Одновременные TCP + WS клиенты | 32 суммарно, включая WS handshake; лишние соединения закрываются |
| Pending-запросы на клиента | 64 |
| Подписки на клиента | 64 ключа |
| Выходной буфер клиента | 64 KiB |
| Очереди команд и наблюдений PortWorker | По 128 элементов на порт |
| Персональная очередь наблюдений | 128 элементов |
## WebSocket

В конфигурации можно добавить второй транспорт к тому же серверу:

```toml
[websocket]
enabled = true
bind = "127.0.0.1:7241"
allowed_origins = ["http://localhost:3000"]
```

Без секции или при `enabled = false` WebSocket выключен. При включении `bind` обязателен:
только числовой loopback IPv4/IPv6, включая порт 0 для выбора ОС. Совпадение с TCP-адресом
при ненулевом порте запрещено. Неизвестные поля отклоняются. Оба listener и SQLite открываются
до физических портов; ошибка любого listener прекращает запуск и освобождает уже открытые ресурсы.
Недоступность отдельного прибора оставляет оба API доступными, а команды к нему возвращают
`runtime_unavailable`.

Endpoint — `ws://127.0.0.1:7241/application/v1`, обязательный подпротокол —
`lab-server.application.v1`. Путь с query string не поддерживается. Один WebSocket Text message
содержит один JSON-запрос; ответ или событие также занимает один Text message, без завершающего LF.
Команды, коды ошибок, `hello.version = 1`, подписки, кеш и правила `set` совпадают с TCP.
Text допускает фрагментацию; Ping/Pong и Close обслуживаются транспортом. Binary закрывает
соединение с кодом 1003, превышение размера — 1009, неверный UTF-8 — 1007, ошибка фрейминга — 1002.

Если клиент передал Origin, требуется точное совпадение с `allowed_origins`; список по умолчанию пуст.
`*` не поддерживается. Отсутствующий Origin разрешён для локальных небраузерных клиентов.
Origin не является аутентификацией. Сервер не реализует TLS или авторизацию и не предназначен
для прямого подключения через интернет. Внешний защищённый прокси может предоставлять WSS;
адаптер не требует специальных заголовков, доменов или настроек конкретного прокси.

Проверка без оборудования, из корня репозитория:

```powershell
$env:CARGO_TARGET_DIR = 'D:\rust_projects\lab-server-agent-build'
cargo run --release -- --config examples/websocket.toml
```

Этот пример содержит пустой каталог. В JavaScript-клиенте со страницы `http://localhost:3000`:

```javascript
const ws = new WebSocket('ws://127.0.0.1:7241/application/v1', 'lab-server.application.v1');
ws.onmessage = event => console.log(JSON.parse(event.data));
ws.onopen = () => {
  ws.send(JSON.stringify({id: 1, op: 'hello'}));
  ws.send(JSON.stringify({id: 2, op: 'describe'}));
  ws.send(JSON.stringify({id: 3, op: 'ping'}));
};
// По окончании: ws.close(1000);
```

Для приборов добавьте секцию `[websocket]` к своей TOML-конфигурации и используйте глобальные ключи
из `describe`.

| Ресурс | Ограничение |
|---|---|
| TCP + WS вместе, включая незавершённые HTTP Upgrade | 32 слота; лишний сокет закрывается |
| Входящий WS message / отдельный frame | по 16 КиБ |
| Прочитанные байты HTTP Upgrade / время Upgrade | 16 КиБ / 5 с |
| Pending / подписки на сессию | 64 / 64 |
| Исходящая очередь Session | 64 КиБ, прежний учёт UTF-8 плюс 1 зарезервированный байт на сообщение |
| Внутренний буфер записи tungstenite | максимум 66 560 байт |
| Сообщение, возвращённое `WriteBufferFull` | не более одного кадра, до размера одного сообщения Session плюс заголовок |
| Буфер чтения tungstenite | начальный размер 4 КиБ; сборка frame/message ограничена указанными лимитами |
| Ожидание отправки одного сообщения / завершение Close | 5 с / 2 с |
| Работа одного клиентского прохода | до 16 сообщений и 64 низкоуровневых I/O-вызовов; ожидание 2 мс |

Это ограничения полезных данных буферов, а не точный предел RAM процесса: дополнительно нужны
метаданные, округление ёмкости аллокатором, стек клиентского потока и системные буферы сокета.
Следующий JSON извлекается из Session только после `flush` предыдущего. При `WouldBlock` кадр
уже принадлежит библиотеке и повторно не ставится; при `WriteBufferFull` сохраняется только
возвращённый кадр. Медленный клиент не блокирует другие клиентские потоки, опрос или Recorder.
За проход основного цикла принимается не более 32 подключений с каждого listener, затем читается агрегатор.

## Общее ядро сессии

`session::Session` принимает один завершённый JSON-текст через `receive_message`,
выдаёт отдельные JSON-сообщения без LF через `next_message` и обслуживает существующие
pending-запросы через `collect_ready`. `bind_observations` связывает сессию с одним
`ObservationReceiver` **до первой подписки**; `collect_observations` читает тот же приёмник
порциями до 32 публикаций. Приёмник нужно сохранять до завершения сессии.

`service::DeviceService` содержит общий `CommandRouter`, каталог, кеш и `ObservationFanout`.
Его `receive_message` передаёт JSON в сессию с этим контекстом. Все транспорты должны
использовать один экземпляр сервиса: второй кеш, агрегатор или обработчик команд не нужен.
`tcp::MultiDeviceTcp` остаётся совместимым именем этого же типа, включая прежние методы TCP.

Пример границы для владельца транспорта (без открытия сокетов или оборудования):

```rust,ignore
use lab_server::session::Session;
use std::time::Instant;

// service: &lab_server::service::DeviceService
let mut session = Session::new(64, 64 * 1024);
let observations = service.register_client()?;
session.bind_observations(&observations);

// Повторяется владельцем транспорта, даже когда новых запросов нет.
session.collect_ready(Instant::now())?;
service.receive_message(&mut session, r#"{"id":1,"op":"hello"}"#, Instant::now())?;
session.collect_observations(&observations)?;
if let Some(json_text) = session.next_message()? {
    // Передать один JSON-текст, ограничивая собственный буфер транспорта.
}
// После чистого EOF: session.close_input(); затем обслуживать pending и выход
// до session.is_finished(). При аварии транспорта владелец освобождает сессию.
```

`protocol::Request`, `parse_request` и `observation_json` общие для всех транспортов;
прежние `TcpRequest`, `parse_tcp_request` и корневой `observation_json` сохранены.
`connection::TcpConnection` сохраняет публичные методы и поле `session`.
`connection::ClientSession` — тот же `SessionState`, с дополнительным состоянием
TCP-адаптера вместо `()`; прежние поля и `receive(bytes)` / `dispatch_incoming` доступны.
Только адаптер содержит NDJSON-декодер, разбирает ошибки фрейминга, дописывает LF и
выполняет частичные записи сокета. Само ядро не использует `TcpStream` или `FrameDecoder`.

Исходящая FIFO хранит законченные тексты, а не слитый поток байтов. Её бюджет по-прежнему
равен **64 КиБ ожидающих отправки байтов: UTF-8 сообщения + 1 байт LF**. Для транспорта
сообщений этот дополнительный байт также резервируется; `next_message` освобождает всю
стоимость сообщения. TCP освобождает только фактически записанные байты, сохраняя позицию
при `WouldBlock`, включая позицию перед LF. Получить целое сообщение после частичной TCP-записи
нельзя: возвращается ошибка, предотвращающая повторную отправку префикса.
Во время частичной записи сохраняется исходный текст переднего сообщения; поэтому хранение
текстов ограничено бюджетом очереди плюс не более одного частично отправленного сообщения
(помимо ограниченных накладных расходов объектов FIFO). Это бюджет ожидающих байтов, а не лимит RAM.

Порядок обслуживания TCP сохранён: готовые завершения pending, ответы на разобранные запросы,
затем наблюдения. ACK подписки предшествует её новым измерениям; номера активации, накопленная
потеря после unsubscribe/subscribe и изоляция портов остались в существующих session/fanout.
Чистый EOF прекращает новые запросы и поток измерений, но позволяет получить окончательные
ответы pending. Терминальная ошибка потока не создаёт фиктивных ответов `set`.
`PendingRequests`, `Pending`, `SetExecution`, таймауты и правила `outcome_unknown` не изменены.

Входной фрейминг и ограничения транспорта реализованы в TCP/WS-адаптерах.
При переполнении выхода ядро становится терминальным; транспорт отправляет уже принятый префикс, если это возможно.
